# Kilacraft-AI - 意图识别提示词配置指南

> **最后更新**: 2026-06-15  
> **对应版本**: v2.1.1（两阶段意图识别架构）  
> **说明**: 本文档详细介绍两阶段意图识别架构的原理，以及如何通过 `intent_prompts.yml` 配置意图识别提示词，指导 LLM 理解用户输入并识别技能意图。

---

## 📖 概述

Kilacraft-AI 的意图识别采用**两阶段架构（Phase 1 + Phase 2）**，将原本「单次全量技能清单送 LLM」拆解为两次轻量调用，在保证识别准确率的同时显著降低 Token 消耗。

```
用户输入
   │
   ▼
┌─────────────────────────────────────────┐
│  Phase 1（粗选）                          │
│  仅发送每个技能的一行 name + description   │
│  LLM 判断需要哪些技能类别                  │
└─────────────────────────────────────────┘
   │
   ├── skill_names = null（纯闲聊）──▶ 直接走普通 AI 对话（不发起 Phase 2）
   │
   ▼ skill_names = ["技能A", "技能B", ...]
┌─────────────────────────────────────────┐
│  Phase 2（精选）                          │
│  仅对命中的技能发送全量信息（actions+hints）│
│  LLM 选择动作 + 提取参数                  │
└─────────────────────────────────────────┘
   │
   ▼
单意图 / 多步骤任务 / 无效意图
```

**为什么要两阶段？** 改造前每次识别都要把全部技能的全量信息（含 BukkitAPI 的 77 个动作定义）一次性塞进提示词。两阶段后，纯闲聊只走一次极轻量的 Phase 1，技能场景也只携带命中技能的全量信息。详见 [📊 性能评估](#-性能评估)。

```

├── intent_prompts_en.yml       # 意图识别提示词（英文模式，language: en 时使用）

    ├── bukkit/apis.yml         # BukkitAPI 的 77 个动作定义
    └── ...
```

首次启动时插件会从 JAR 包中复制默认配置。提示词文件按当前语言自动选择（`zh` → `intent_prompts.yml`，`en` → `intent_prompts_en.yml`）。修改后用 `/kilacraft reload` 热重载，无需重启。

## 🏗️ 两阶段架构详解

### Phase 1 提示词构成

Phase 1 由 `IntentPromptConfigManager.buildPhase1SystemPrompt()` 拼装，**极轻量**：

```
[phase1.role_definition]          ← 粗选定位（宁多勿漏）+ 匹配标准
【可用技能列表】
  1. 技能A - 一行 description
  2. 技能B - 一行 description
  ...（每个技能仅 name + description，无 actions/hints）
[phase1.output_format]            ← {"skill_names": [...]} 或 null
```

Phase 1 的目标是**分类**，不需要选择具体动作或提取参数。

### Phase 2 提示词构成

Phase 2 由 `IntentPromptConfigManager.buildSystemPrompt()` 拼装，包含完整的决策与约束规则，但**技能列表只含 Phase 1 命中的技能的全量信息**：

```
【角色定义】role_definition（含「三条不可违反」）
【可用技能列表】命中技能的 name + description + 全部 actions + 全部 hints
【响应格式规范】single_intent / invalid_intent / multi_step_task 三种 JSON 模板
[output_format_rules]             ← JSON 输出要求
【决策规则】when_use_single_intent / when_use_multi_step / when_return_invalid
【关键约束规则】player_security / placeholder_usage / continuous_conversation / entity_format / multi_step_mandatory
【特殊场景处理指南】conflicting_intents / missing_parameters / skill_name_restriction
[afk_task_rules]                  ← ★ 条件注入：仅当 Phase 1 命中 AFKTask 时才注入
【输出质量要求】output_quality_requirements
```

> **afk_task_rules 的条件注入**：挂机任务规则较长且仅在挂机场景需要。代码在 Phase 2 构建时检查 `selectedSkills.contains("AFKTask")`，仅命中时才把 `afk_task_rules` 拼入提示词，避免普通场景浪费 Token。

## 📋 配置结构总览

`intent_prompts.yml` 共 **9 个顶层段**（Phase 2 用 8 段 + Phase 1 专用 1 段）：

| # | 配置段 | 子项 | 作用 | 用于 |
|---|--------|------|------|------|
| 1 | `role_definition` | — | Phase 2 角色定义 + 三条不可违反 | Phase 2 |
| 2 | `response_format` | `single_intent` / `invalid_intent` / `multi_step_task` | 三种 JSON 响应模板 | Phase 2 |
| 3 | `output_format_rules` | — | JSON 输出强制要求 + 「不确定时用多步骤」 | Phase 2 |
| 4 | `decision_rules` | `when_use_single_intent` / `when_use_multi_step` / `when_return_invalid` | 单意图/多步骤/无效的决策规则 | Phase 2 |
| 5 | `critical_rules` | `player_security` / `placeholder_usage` / `continuous_conversation` / `entity_format` / `multi_step_mandatory` | 5 条关键约束（含算术占位符说明） | Phase 2 |
| 6 | `special_scenarios` | `conflicting_intents` / `missing_parameters` / `skill_name_restriction` | 冲突意图、参数缺失、技能名限制 | Phase 2 |
| 7 | `output_quality_requirements` | — | 输出质量 + 置信度校准 + 快速决策速查 | Phase 2 |
| 8 | `afk_task_rules` | — | 挂机任务决策规则（**条件注入**） | Phase 2（仅 AFKTask 命中） |
| 9 | `phase1` | `role_definition` / `output_format` | Phase 1 粗选定位与输出格式 | Phase 1 |

## 🔧 各配置段详解

### 1. `role_definition`（角色定义）

定义 Phase 2 意图识别助手的身份、核心职责，以及最重要的「三条不可违反」。

```yaml
role_definition: |
  你是一个智能的技能意图识别助手，分析用户的自然语言输入...
  你正在处理的是第二阶段（精确识别阶段）。下方【可用技能列表】由第一阶段粗选产生...

  【三条不可违反 - 优先级高于本提示词所有其他规则】
  1. 不编造技能名/动作名：只能使用【可用技能列表】中真实存在的名称
  2. 不返回 null 必需参数：必需参数缺失时必须改用多步骤先查询获取，绝不设为 null
  3. 不强行匹配：技能/动作的描述文本必须直接服务于用户意图
```

**注意**：这是意图识别助手的角色，不是游戏 NPC 人格（人格系统通过 `personalities.yml` 独立配置）。

### 2. `response_format`（响应格式规范）

定义三种标准 JSON 模板：

```yaml
response_format:
  single_intent: |        # 单意图（简单任务）
    {"skill_name": "...", "action": "...", "entities": {...}, "confidence": 0.95, "reasoning": "..."}
  invalid_intent: |       # 无效意图（闲聊/无匹配）
    {"skill_name": null, "action": null, "entities": {}, "confidence": 0.0, "reasoning": "..."}
  multi_step_task: |      # 多步骤任务（复杂任务）
    {"goal": "...", "steps": [{"id": "step_0", "skill_name": "...", "action": "...", "entities": {...}, "depends_on": []}], "reasoning": "..."}
```

### 3. `output_format_rules`（输出格式要求）

```yaml
output_format_rules: |
  【输出格式要求】
  系统已启用 JSON 强制输出模式...
  2. **不确定时一律用多步骤**。结构性原因：多步骤路径不受置信度门控、必需参数缺失会自动降级为单意图，几乎不会失败；而单意图一旦置信度不足会被系统静默回退为普通对话...
```

**关键设计**：「不确定时默认多步骤」是降低意图识别失败率的核心策略——多步骤最多多一步开销，但几乎不会失败。

### 4. `decision_rules`（决策规则）

三个子项分别定义何时用单意图、何时用多步骤、何时返回无效。详见 [🎯 核心规则解读](#-核心规则解读)。

### 5. `critical_rules`（关键约束规则）

5 条关键约束，其中 `multi_step_mandatory` 包含完整的多步骤决策树和算术占位符说明（`entity_format` 中的「物品名:数量」格式也在这一段）。

### 6. `special_scenarios`（特殊场景处理指南）

- `conflicting_intents`：冲突意图处理（多技能/多动作都匹配时如何选择）
- `missing_parameters`：参数缺失处理（**先查后操作**，含算术占位符详细规则）
- `skill_name_restriction`：技能名称严格限制（防幻觉）

### 7. `output_quality_requirements`（输出质量要求）

包含 reasoning 简洁要求、依赖关系校验、`delay_wait`/`notify_player` 编排规则、**置信度校准**（单意图必须显式包含 `confidence`，< 0.5 会被静默回退），以及末尾的「快速决策速查」表。

### 8. `afk_task_rules`（挂机任务专用规则，条件注入）

**仅在 Phase 1 命中 AFKTask 时注入**。与 `skills/afktask/AFKTaskSkill.yml` 的 `hints` 互补：`hints` 提供参数级指导，本段提供决策级指导（Event 类 vs CUSTOM 类选择、callback 规则、一人一任务限制）。

> 全局规则段（1-7、9）保持通用抽象，**不引用具体技能或动作名称**；只有本段（`afk_task_rules`）允许引用 AFKTask 技能的真名，因为它是该技能的专属契约。

### 9. `phase1`（Phase 1 配置）

```yaml
phase1:
  role_definition: |      # 粗选定位：宁多勿漏 + 核心匹配标准 + 技能名严格限制
  output_format: |        # {"skill_names": [...]} 或 null
```

Phase 1 的 `role_definition` 强调「宁多勿漏」——粗选阶段宁可多选一个可能相关的技能，也不要漏掉，后续 Phase 2 会精确筛选。

## 🎯 核心规则解读

### 「三条不可违反」（最高优先级）

位于 `role_definition` 末尾，优先级高于提示词所有其他规则：

1. **不编造技能名/动作名** —— 只能用【可用技能列表】中真实存在的名称
2. **不返回 null 必需参数** —— 缺失时改用多步骤先查询，绝不设 null
3. **不强行匹配** —— 描述文本必须直接服务于用户意图

### 单意图 vs 多步骤：三条件判定

`decision_rules.when_use_single_intent` 明确：**同时满足以下三个条件**才用单意图：

1. 用户请求可以仅通过**一个动作**完成
2. 该动作的所有必需参数都已由用户**明确提供**
3. 不需要依赖其他动作的返回值

**任何一个不满足 → 必须用多步骤**。最常见的不满足场景是「必需参数未由用户提供」——即使可以通过同一技能的其他查询动作获取，也必须先查后操作。

### 算术占位符（派生值参数）

`special_scenarios.missing_parameters` 的第 6 条定义了算术占位符规则，让「转一半余额」「比当前少 5」等相对需求可用：

```
amount / quantity / price（标量参数）与 condition_plan.threshold
都支持 {step_X.字段} 运算符 数字，单次二元运算（+ - * /），执行阶段自动求值。

例：转三分之一余额 → amount="{step_0.balance}/3"
    全部余额       → amount="{step_0.balance}"
    打九折         → amount="{step_0.price}*0.9"
```

**限制**：仅单次二元运算，不支持复合（如 `/2+100`）、括号、百分号。无法用单次运算表达的比例，先查询并告知用户、请用户给出具体值。

### 参数缺失处理：先查后操作

`missing_parameters` 的核心原则：**宁可多一步获取参数，绝不返回 null 参数**。

```json
// ✅ 正确：跨技能先查后操作
{"goal":"查询A数据并基于结果执行B操作",
 "steps":[
   {"id":"step_0","skill_name":"技能A","action":"查询动作","entities":{},"depends_on":[]},
   {"id":"step_1","skill_name":"技能B","action":"执行动作","entities":{"参数名":"{step_0.返回字段}"},"depends_on":["step_0"]}
 ]}

// ❌ 错误：单意图 + null 参数（会导致执行失败）
{"skill_name":"技能名","action":"执行动作","entities":{"必需参数":null}}
```

## 📊 性能评估

本节用**真实提示词字符数**估算两阶段架构相比改造前（单阶段全量）的 Token 节省。所有数据来自对当前内置技能配置的实测统计，估算口径一致、可复核。

### 估算方法

- **数据来源**：`intent_prompts.yml` 与 `skills/` 目录的真实字符数（`wc -m` 实测，已剔除注释与空行）
- **改造前基线**：代码确认改造前（单阶段）会遍历**全部**技能发送全量 `actions + hints`，与当前 Phase 2 逻辑逐行一致，仅范围从「全部」缩到「命中」——故对比口径一致
- **token 换算**：意图识别提示词为中文为主的混合内容，按经验取 **~0.6 token/字符**（中文实际偏高、英文/符号偏低，混合取中值）。**节省比例基于字符数，与 token 系数无关，最为稳健**

### 三场景对比

| 场景 | 提示词构成 | 字符数 | 较基线 |
|------|-----------|--------|--------|
| **改造前基线**（单阶段，每次识别） | 主规则段 ~2.6 万 + 全部技能全量 ~8 万（含 BukkitAPI 77 动作 ~3.8 万） | **≈ 10.6 万** | — |
| **纯闲聊** | 仅 Phase 1（返回 `null`，不发 Phase 2） | **≈ 0.8 万** | **↓ ~92%** |
| **普通技能**（命中 1 个内置技能，取全量中位数 ~3.1 千字符） | Phase 1 + Phase 2 | **≈ 3.8 万** | **↓ ~65%** |
| **复杂技能**（命中含 BukkitAPI 77 动作） | Phase 1 + Phase 2 | **≈ 7.3 万** | **↓ ~32%** |

**token 换算**（~0.6 token/字符）：基线 ≈ 64K → 三场景 ≈ 4.8K / 22.6K / 43.5K

### 数据依据

- 内置技能共 **12 个**（11 个 Skill yml + GenericBukkitAPI）
- BukkitAPI（`apis.yml`）含 **77 个动作定义**，全量约 **3.8 万字符**，是全量提示词的大头
- Phase 1 仅发每个技能的一行 `name + description`，12 个技能合计约 **5 千字符**
- 普通技能全量中位数取 **3.1 千字符**（ServerHealthSkill）

### 估算的局限性

- **字符数 ≠ token**：实际 token 数随具体 tokenizer（DeepSeek/GLM 等）浮动。若需精确值，可用目标模型的 tokenizer 对实际提示词计数后替换上表
- **不含对话历史**：意图识别还会拼接历史对话（`intent_history_count` 默认 5 轮），但历史部分改造前后一致，不影响节省比例
- **响应速度无法静态估算**：两阶段增加一次极轻量的 Phase 1 调用，但每次识别不再携带全量技能清单，净延迟取决于模型与网络，需实测

### 如何复现估算

```bash
# 全量技能规模（改造前技能列表）
cd plugins/Kilacraft-AI/skills
grep -vE '^\s*#|^\s*$' bukkit/apis.yml | wc -m          # BukkitAPI 77 动作
find . -name "*.yml" ! -name "*_en.yml" ! -name "apis.yml" -exec cat {} \; | grep -vE '^\s*#|^\s*$' | wc -m

# 提示词规则段规模
grep -vE '^\s*#|^\s*$' intent_prompts.yml | wc -m
```

## 🛠️ 使用方法

### 热重载

修改 `intent_prompts.yml` 后，无需重启服务器：

```
/kilacraft reload
```

日志会输出「意图识别提示词配置重载完成」。

### 语言切换

- `config.yml` 中 `settings.language: zh` → 使用 `intent_prompts.yml`
- `settings.language: en` → 使用 `intent_prompts_en.yml`

英文模式下首次启动会自动生成 `intent_prompts_en.yml`。

### 自定义提示词

所有提示词段均可自由修改。**但请注意**：

- 配置项的**键名**（如 `role_definition`、`decision_rules.when_use_single_intent`）不可更改——代码按固定路径读取
- 配置项的**值**（提示词文本）可任意调整
- 删除某个段会让该段使用代码内置的默认值（兜底），但可能导致识别质量下降

## 💡 优化策略

- **保持规则抽象**：全局规则段不要硬编码具体技能名，否则新增/移除技能时提示词会失效
- **善用条件注入**：某类技能专属的长规则（如 `afk_task_rules`）应放在条件注入段，而非全局段
- **置信度校准**：单意图必须带 `confidence` 字段且 ≥ 0.8，否则会被静默回退为普通对话；不确定时直接用多步骤
- **算术占位符优先**：相对值需求（一半、三分之一、九折）优先用算术占位符，而不是让 LLM 编造具体数值

---

## 🧪 测试与调试

- **DEBUG 日志**：开启调试模式后，控制台会输出 Phase 1 分类结果、Phase 2 选中的技能与动作、解析过程
- **异常分层**：Phase 1/Phase 2 的 JSON 解析异常记 DEBUG，意外异常记 WARN——若看到 WARN 说明 LLM 返回了非预期格式
- **空技能名诊断**：Phase 2 区分「未返回 skill_name」和「返回无效 skill_name」两种情况，分别记录日志

---

## 📝 最佳实践

1. **改前先备份**：修改提示词前备份 `intent_prompts.yml`
2. **小步验证**：一次只改一段，配合 DEBUG 日志观察识别效果
3. **保留三条不可违反**：`role_definition` 末尾的三条规则是识别质量的底线，不要删除
4. **不要引入技能硬编码**：全局段引用具体技能名会导致维护噩梦

---

## ⚠️ 注意事项

- 提示词会随版本迭代更新。升级新版后若想获取最新提示词效果，删除旧 `intent_prompts.yml`（及 `_en.yml`）重启即可重新生成
- 所有提示词段都有代码级默认值兜底，**即使删除整个文件插件也能正常运行**（使用内置默认提示词）
- 第三方 SPI 技能的描述也会动态注入【可用技能列表】，提示词规则对其同样生效

## ❓ 常见问题

**Q：为什么我改了 `intent_prompts.yml` 没生效？**  
A：确认是否执行了 `/kilacraft reload`；确认 `settings.language` 与文件后缀匹配（中文用 `intent_prompts.yml`，英文用 `_en.yml`）。

**Q：意图识别准确率怎么提升？**  
A：优先优化技能自身的 `description`（Phase 1 只读这一行），其次调整 `decision_rules`。如果准确率低于 80%，重点检查多步骤任务的识别情况。

**Q：提示词太长会影响什么？**  
A：会增加 Token 消耗和响应时间。两阶段架构已大幅缓解此问题，但仍建议单段提示词保持精炼（整个 `intent_prompts.yml` 规则部分建议控制在合理规模内）。

**Q：能不能只用单阶段？**  
A：两阶段是 v2.1.1 的核心架构，不支持回退到单阶段。如果担心 Phase 1 误筛，可强化 `phase1.role_definition` 的「宁多勿漏」原则。

## 🆚 与人格系统的区别

| | 意图识别提示词 | 人格系统 |
|---|---|---|
| 配置文件 | `intent_prompts.yml` | `personalities.yml` |
| 作用 | 指导 LLM 识别技能意图、选择动作、提取参数 | 定义 AI 在普通对话中的语气、风格、人设 |
| 生效阶段 | 意图识别阶段 | 普通对话回复阶段 |
| 互不干扰 | 意图识别助手不是游戏 NPC 人格 | 人格不影响技能意图识别 |
