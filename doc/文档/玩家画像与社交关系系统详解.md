# Kilacraft-AI - 玩家画像与社交关系系统详解

> **最后更新**: 2026-08-04  
> **说明**: 本文档详细介绍 Kilacraft-AI 的玩家画像系统、社交关系图谱和服务器事件采集系统

---

## 📖 概述

v2.0.0 引入了三大数据驱动子系统，让 AI 记住每个玩家的行为偏好、追踪玩家间的社交关系，并自动记录服务器里程碑事件。这些系统共享数据库持久化层，协同工作让 AI 越来越懂你的玩家。

---

## 🧠 玩家画像系统

### 核心设计

玩家画像是 AI 对玩家的“长期记忆”。系统在玩家登录及后续对话累积时**尝试**触发 LLM 分析（受三重门控约束，未达条件则跳过），生成结构化的八维度画像，并在后续对话中动态注入**user 消息**（system 提示词保持纯静态以最大化上下文缓存命中），让 AI 的服务更个性化。

### 画像维度（八维度）

| 维度 | JSON Key | 说明 | 示例 |
|------|------|------|------|
| 游戏风格 | playstyle | 玩家的玩法偏好 | PVP 狂热者 / 建筑大师 / 红石工程师 |
| 性格特征 | personality | 行为模式 | 冒险型 / 社交型 / 谨慎型 |
| 兴趣偏好 | interests | 感兴趣的领域和活动 | 经济交易 / 红石 / 建筑 |
| 交互禁忌 | boundaries | 玩家不喜欢的内容或行为 | 不要称呼名字 / 不要催促 |
| 回复偏好 | communication | 期望 AI 的回复方式 | 简洁直接 / 不用 emoji |
| 空间记忆 | spatial | 提到的地点、基地位置 | 主基地在沙漠腹地 |
| 已知事实 | facts | 玩家明确声明的事实 | Steve 是好友 / 家在沙漠神殿旁 |
| 特别观察 | notes | LLM 自由观察 | “该玩家最近对附魔系统特别感兴趣” |

### 工作流程

```
玩家登录 → 加载内存缓存 → 检查是否需要分析（三重门控）
                              ↓ 是
                    判断是否有旧画像（extendedData）
                         ↙            ↘
                    首次分析           增量分析
                  （无旧画像）       （有旧画像）
                    ↓                    ↓
                LLM 分析             LLM 融合
              （首次提示词）       （旧画像 + 新对话）
                    ↓                    ↓
                    └──────┬─────────────┘
                           ↓
                    递增 version（+1）
                    注入 analyzed_at 时间戳
                           ↓
                    更新内存缓存
                    异步写入 DB（player_profile）
                    异步写入快照（profile_snapshot）v2.0.2 新增
                           ↓
                    下次对话时画像摘要注入 user 消息（system 提示词保持纯静态以最大化上下文缓存命中）
```

**v2.0.2 新增 — 增量分析机制**：

v2.0.2 之前，LLM 每次只看到近期对话，输出全新画像全量覆盖旧数据，前一次的认知全部丢失。v2.0.2 引入两层改造：

1. **输入端 — 旧画像注入**：非首次分析时，将旧画像 JSON 注入 LLM 输入，LLM 在已有认知上叠加新观察，而非从零开始
2. **输出端 — 版本递增**：`version` 字段从硬编码 `1` 改为自动递增（`oldVersion + 1`），每次分析产生一个新版本

**双提示词系统**：

| 场景 | 使用的提示词 | 说明 |
|------|------------|------|
| 首次分析（无旧画像） | `DEFAULT_SYSTEM_PROMPT` | 原始提示词，要求输出八维度 JSON |
| 增量分析（有旧画像） | `DEFAULT_INCREMENTAL_SYSTEM_PROMPT` | 要求对比旧画像 + 新对话，融合输出更新后的完整画像 |

两种提示词均可在 `database.yml` 中自定义覆盖（中文/英文各一套）。有自定义值时优先使用自定义值，否则使用内置默认值。

**增量分析的递进效果**：
- V1 分析：对话A → 画像V1（首次建立）
- V2 分析：画像V1 + 对话B → 画像V2（V1 的认知被带入 LLM，保留在 V2 中）
- V3 分析：画像V2 + 对话C → 画像V3（V1+V2 的认知被保留）

画像信息是累积的，不会丢失。一个玩了半年建筑的玩家，最近两天打了下 PvP，画像会在原有基础上融合更新，而非从"建造大师"直接变成"战斗狂"。

### 三重门控机制

为防止不必要的 LLM 开销，画像分析需要**三者同时满足**才触发：

1. **时间间隔**：距上次分析 ≥ `analysis_interval_days` 天（默认 1 天）
2. **消息数量**：自上次分析以来玩家主动发言（chat/command）≥ `min_messages_to_trigger` 条（默认 10）
3. **消息窗口**：加载上次分析时间点之后**全部**新消息（无数量上限），不存在固定条数的滑动窗口

### 版本戳防竞态

画像缓存清理采用内存版本戳机制——玩家登出时不立即清理缓存，而是延迟 5 分钟后检查版本戳。如果玩家在延迟期间重新连接，版本戳已变更，跳过移除。此机制防止快速重连时缓存被误清除。数据库更新使用 `profileDao.update()` 全字段写入，无需乐观锁。

### 画像版本追踪 `v2.0.2 新增`

v2.0.2 之前，`version` 字段硬编码为 `1`，从未真正递增。v2.0.2 改为从内存中的 `extendedData` 读取旧版本号，每次分析自动 +1 递增。首次分析时 `oldVersion = 0`，`newVersion = 1`。

### 历史快照 `v2.0.2 新增`

每次画像分析完成后，系统在写入 `player_profile` 的同时，自动向 `kca_profile_snapshot` 表插入一条快照记录，记录本次分析的完整画像 JSON、版本号、分析窗口时间范围和消息条数。

**快照与画像更新的关系**：

| 操作 | 目标表 | 说明 |
|------|--------|------|
| `profileDao.updateProfileData()` | `kca_player_profile` | 更新 `profile_data` + `profile_analyzed_at`（覆盖式） |
| `snapshotDao.insert()` | `kca_profile_snapshot` | 插入一条历史快照（追加式，永久保留） |

两个操作在同一个 IO 任务的同一个 `Connection` 中串行执行，保证数据一致性。快照表永久保留，不纳入 `DataCleanupService` 定时清理。

### 内存缓存

画像数据在内存中缓存，秒级响应。写入异步进行，不影响玩家体验。

## 🕸️ 社交关系图谱

### 核心设计

社交关系图谱追踪玩家间的互动，自动计算关系强度，形成动态社交网络。每日自动衰减弱化不活跃的关系。

### 交互权重

| 交互来源 | 权重 | 触发方式 |
|----------|:---:|----------|
| 私聊（/tell、/msg） | +0.01 | 自动监听聊天事件 |
| TPA 传送 | +0.02 | 自动监听 CMI TPA 命令 |
| Skill 交互（白名单） | +0.005 | SocialRelationExtractor 定期扫描 kca_skill_log |

### 每日衰减

```
新强度 = 当前强度 × 0.95（每日衰减 5%）
```

衰减后强度 < 阈值（如 0.01）的关系自动清理，保持数据新鲜度。

### 分布式安全机制

#### 问题
多子服环境下，多个服务器可能同时执行每日衰减，导致重复衰减。

#### 解决方案
- **水位标记表**（kca_watermark）：衰减水位名固定为 `decay_date`（全局唯一）
- **DB 行锁**（`SELECT FOR UPDATE`）：开始衰减前加锁，检查水位日期是否为今天
- **CAS 互斥**（TaskScheduler 层）：单服内同一任务同一时间只有一个线程执行

两层互斥保护确保多子服环境不冲突。社交关系天然跨服共享（无 server_id 字段），衰减对全表操作，全局只执行一次。

### 社交关系提取器

`SocialRelationExtractor` 定期扫描 `kca_skill_log` 表，查找白名单 Skill 中涉及"玩家-玩家"互动的记录（如传送、交易等），自动增强对应玩家间的社交关系。

**白名单 Skill 示例**：
- `cmi.send_tp_request`（TPA 传送请求）
- `command.execute_command` 中的 `/tpa` 类命令

### 对话中的社交感知

AI 问候语可引用社交关系：
> "欢迎回来！你的好友 Steve 也在线。你们最近交流很频繁呢。"

## 📡 服务器事件采集系统

### 核心设计

自动记录服务器中发生的里程碑事件，让玩家离线后也能回顾"错过了什么"。

### 事件类型

事件采集系统（`EventCollector` + `MarketEventCollector`）监听 Bukkit 事件并写入 `kca_server_event` 表。按来源分组：

**生命周期**（登录监听器写入）

| 事件类型 | 触发条件 | 记录内容 |
|----------|---------|---------|
| `PLAYER_LOGIN` | 玩家登录 | 登录时间 |
| `PLAYER_LOGOUT` | 玩家登出 | 登出时间、所在世界/坐标 |
| `PLAYER_FIRST_JOIN` | 首次加入服务器 | 首次登录时间 |

**玩家成就与行为**（`EventCollector` 监听对应 Bukkit 事件）

| 事件类型 | 触发条件 | 记录内容 |
|----------|---------|---------|
| `PLAYER_DEATH` | 玩家死亡 | 死亡位置、死因 |
| `PLAYER_PVP_KILL` | PVP 击杀其他玩家 | 击杀目标、武器 |
| `PLAYER_PVP_DEATH` | 被 PVP 击杀 | 凶手 |
| `PLAYER_ADVANCEMENT` | 解锁成就（过滤配方类） | 成就名称、描述 |
| `PLAYER_LEVEL_UP` | 升级 | 旧等级、新等级 |
| `PLAYER_USE_TOTEM` | 使用不死图腾复活 | — |
| `PLAYER_DEFEAT_BOSS` | 击败 BOSS（末影龙/凋灵/监守者/远古守卫者） | BOSS 类型 |
| `PLAYER_PET_DEATH` | 驯服的宠物死亡 | 宠物类型 |
| `PLAYER_COMPLETE_RAID` | 完成袭击 | 袭击位置 |
| `PLAYER_TOOL_BREAK` | 工具耐久耗尽损毁 | 物品类型 |
| `PLAYER_CATCH_TREASURE` | 钓到宝藏物品 | 物品类型 |
| `PLAYER_LIGHTNING_STRIKE` | 被雷劈中 | — |
| `PLAYER_CURE_VILLAGER` | 治愈僵尸村民 | — |
| `PLAYER_MINE_ANCIENT_DEBRIS` | 挖到远古残骸 | — |
| `PLAYER_TAME_ANIMAL` | 驯服动物 | 动物类型 |
| `PLAYER_CRAFT_ENCH_GOLDEN_APPLE` | 合成附魔金苹果 | — |
| `PLAYER_BUILD_WITHER` | 召唤凋灵 | — |

**市场**（`MarketEventCollector`，需集成 GlobalMarketPlus）

| 事件类型 | 触发条件 | 记录内容 |
|----------|---------|---------|
| `MARKET_ITEM_LISTED` | 上架商品 | 商品名、价格、数量 |
| `MARKET_ITEM_SOLD` | 商品售出 | 商品名、价格、买家 |
| `MARKET_MONEY_RECEIVED` | 收到售货款项 | 金额、商品 |

**系统/管理**（服主管理子系统写入，非 EventCollector）

| 事件类型 | 触发条件 | 记录内容 |
|----------|---------|---------|
| `HEALTH_ALERT` / `HEALTH_ALERT_NOTIFIED` | 服务器健康告警/告警已通知 | 告警摘要 |
| `UPDATE_AVAILABLE` / `UPDATE_NOTIFIED` | 检测到新版本/已通知管理员 | 版本号 |

**玩家自定义监听**（监听系统触发时写入）

| 事件类型 | 触发条件 | 记录内容 |
|----------|---------|---------|
| `PLAYER_WATCH_TRIGGERED` | 玩家设定的监听条件命中 | 监听详情 |

> 命名细节：`PLAYER_LEVEL_UP`（带下划线）、`MARKET_ITEM_SOLD`（非 `MARKET_SELL`）。完整字段结构见《数据库与持久化配置指南》。

### 离线事件聚合器

玩家上线时，系统采用三大分类架构查询离线期间发生的事件，生成摘要供 AI 问候语使用：

```
玩家: [登录]
系统: 三大分类数据聚合
  → 分类一（自己）：你的钻石已售出（+$500）
  → 分类二（好友）：Steve 达成了 2 个成就，Alex 升了 3 级
  → 分类三（摘要）：累计登录 100 次里程碑！上次游玩击败了末影龙
  → 使用这些信息生成登录问候语
```

事件数量和类型可通过 `behavior.yml` 的 `greeting` 段配置，好友动态通过 LEFT JOIN `kca_player_profile` 获取玩家名。

```
│                   Bukkit 事件层               │
│  PlayerJoin/Quit, Chat, PlayerDeath, CMI... │
└─────────────────┬───────────────────────────┘
                  ↓
┌─────────────────────────────────────────────┐
│              事件采集 & 社交监听               │
│  EventCollector  │  SocialGraph  │  CMI事件  │
└─────────────────┬───────────────────────────┘
                  ↓
┌─────────────────────────────────────────────┐
│              内存缓存层（秒级访问）             │
│  ProfileCache  │  SocialGraph(memory)        │
└─────────────────┬───────────────────────────┘
                  ↓
┌─────────────────────────────────────────────┐
│            数据库异步写入（Write-Behind）       │
│  kca_player_profile │ kca_social_relation    │
│  kca_server_event   │ kca_skill_log          │
│  kca_profile_snapshot v2.0.2 新增             │
└─────────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────────┐
│            LLM 画像分析 + AI 对话注入          │
│  画像摘要注入 user 消息（system 保持纯静态）   │
│  社交关系注入登录问候语                         │
│  离线事件注入回归问候                           │
└─────────────────────────────────────────────┘
```

## 🔧 配置参考

### 画像分析配置（database.yml）

画像分析的全部配置集中在 `database.yml` 的 `profile` 段（早期版本曾放在 `llm.yml` 的 `agent.profile`，已迁移）：

```yaml
profile:
  analysis_interval_days: 1          # 分析触发间隔（天）：距上次分析至少间隔 N 天才再次触发
  min_messages_to_trigger: 10        # 触发分析所需最少新消息数
  analysis_timeout_seconds: 120      # LLM 分析超时（秒）

  # 首次分析提示词（无旧画像时生效）
  analysis_system_prompt: |
    ...（八维度输出 + 数据性质红线，完整内容见 database.yml 或《数据库与持久化配置指南》）
  analysis_system_prompt_en: |
    ...
  # 增量分析提示词（有旧画像时生效，v2.0.2 引入）
  incremental_system_prompt: |
    ...
  incremental_system_prompt_en: |
    ...
```

> 三重门控参数：`analysis_interval_days`（时间间隔）+ `min_messages_to_trigger`（消息数量）共同决定是否触发分析。修改后 `/kila reload` 生效。

### 社交关系配置（内部参数）

社交关系权重和衰减率目前由代码内部控制，未来版本可能开放 YAML 配置。当前默认值：
- 私聊权重：0.01
- TPA 权重：0.02
- Skill 交互权重：0.005
- 日衰减率：5%（每日衰减因子 0.95）
- 弱关系清理阈值：0.01

> v2.2.0 起，参与社交提取的 Skill 白名单在 `config.yml` 的 `social.skill_whitelist` 配置（默认含 `market_action`、`cmi`、`player_watch`）。

### 问候与离线事件（behavior.yml）

问候配置整合在 `behavior.yml` 的 `greeting` 段（早期版本为独立的 `greeting.yml`，已合并进 `behavior.yml`，与推荐/监听/工具通知同文件）：

```yaml
greeting:
  enabled: true
  delay_ticks: 100                   # 登录后延迟多少 tick 发起问候（等玩家完全进服）
  greeting_cooldown_minutes: 30       # 问候冷却（分钟）
  max_own_offline_events: 20          # 玩家自己离线事件最大条数（分类一）
  max_friend_offline_events: 10       # 好友动态最大条数（分类二）
  max_summary_events: 5              # 上次游玩亮点最大条数（分类三）
  profile_injection_enabled: true     # 是否把玩家画像注入问候提示词
  server_info: ""                     # 服务器自定义信息（注入问候）
  first_login_prompt: |               # 首次登录问候提示词
    ...
  returning_login_prompt: |           # 回归登录问候提示词
    ...
```
