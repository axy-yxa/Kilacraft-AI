## 🔄 三种交互模式总览

| 模式 | 触发方式 | Agent能力 | 知识库检索 | 回调机制 | 典型场景 |
|------|---------|----------|-----------|---------|----------|
| **ChatListener** | `@ai` 关键词 / 连续对话 | ✅ 启用 | ✅ 智能注入 | ❌ 不需要 | 玩家主动交互 |
| **KilacraftCommand** | `/kila <消息>` | ✅ 启用 | ✅ 智能注入 | ❌ 不需要 | 服主/管理员查询 |
| **插件命令** | `/kila plugins ...` | ❌ 禁用 | ✅ 普通检索 | ✅ 必须 | 第三方插件集成 |

## 📊 模式 1 & 2：ChatListener / KilacraftCommand（Agent 开启）

这两种模式共享相同的 Agent 处理流程，区别仅在于触发方式。

### 完整调用链路

```
用户输入: "@ai 我手上是什么?这个能卖多少钱?"
  ↓
【1. 入口层】ChatListener / KilacraftCommand
  ├─ 检查权限和冷却时间
  ├─ 发送“正在思考...”提示
  └─ 获取历史对话记录
  ↓
【2. 意图识别层】SkillIntentRecognizer（两阶段）
  ├─ Phase 1（粗选）：仅发送每个技能的一行 name+description，LLM 判断需要哪些技能类别
  │   └─ 返回 null（纯闲聊）→ 跳过 Phase 2，直接走普通 AI 对话
  ├─ Phase 2（精选）：仅对 Phase 1 命中的技能发送全量信息（actions + hints + 可选动态上下文）
  │   ├─ 可选：命中实现 DynamicContextProvider 的技能时，注入其运行时动态内容（如可监听列表）
  │   └─ 对 skill_name 做白名单校验，无效名称拒绝执行
  ├─ 解析 JSON 响应
  └─ 判断任务类型
       ├─ 单意图 → SkillIntent
       ├─ 多步骤 → TaskPlan
       └─ 无效意图 → 回退到普通 AI
  ↓
【3a. 技能执行层】(如果有有效意图)
  ├─ 单意图路径:
  │   ├─ SkillManager.executeSkillByIntent()
  │   ├─ 执行具体 Skill (如 get_player_hand_item、command.execute_command)
  │   └─ 返回 SkillResult { message, data }
  │
  └─ 多步骤路径:
      ├─ TaskExecutor.executeTask()
      ├─ 按依赖顺序执行多个 Skill
      ├─ 数据自动流转 ({step_1.xxx} → step_2)
      │  └─ 支持数组索引访问：{step_1.warps[0].warp_name}
      └─ 返回综合结果
  ↓
【3b. 二次分析层】LLMOutputCoordinator ✨ 中间协调层
  ├─ LLMAnalysisService.analyzeResultWithHandler() 分析执行结果
  │   ├─ 构建分析提示词:
  │   │   ├─ [历史记录] (最近 N 轮对话)
  │   │   ├─ [执行结果] (Skill 返回的结构化数据)
  │   │   └─ [知识库上下文]
  │   │        └─ 检索相关知识片段
  │   │           (服务器规则、物品说明等)
  │   ├─ 调用 LLM 综合分析
  │   └─ 生成自然语言回复
  │
  └─ LLMOutputCoordinator 统一调度输出 ✨ 新增！
      ├─ 根据配置自动判断流式/非流式输出
      ├─ 流式模式:
      │   ├─ 启动 AIResponsePipeline.startStream()
      │   ├─ 实时接收 LLM 片段 → updateStream()
      │   └─ 完成输出 → completeStream()
      └─ 非流式模式:
          └─ 直接调用 AIResponsePipeline.send()
  ↓
【4. 响应层】AIResponsePipeline ✨ 统一输出管线
  ├─ 根据场景选择输出载体（CHAT/ACTION_BAR/BOSS_BAR/TITLE/SIDEBAR）
  ├─ 场景配置：NORMAL_CHAT / SKILL_RESULT / TASK_RESULT / GUARDIAN / GREETING / ERROR
  ├─ 公屏广播：强制使用 CHAT 载体 + AI 前缀（避免覆盖其他玩家的私有载体）
  ├─ 思考消息：使用动态配置的 thinking_channel
  ├─ 流式输出（可选，全场景支持）：
  │   ├─ StreamOutputManager 管理窗口期状态（状态机：IDLE → GENERATING → COMPLETED）
  │   ├─ 请求发起 → 显示"✍️ AI 正在生成中..."占位符
  │   ├─ 接收 SSE 片段 → 实时更新载体（支持 SIDEBAR 自动分页）
  │   └─ 流式完成 → 根据配置决定是否保留最终结果
  └─ MessageDispatcher 智能路由到不同载体（封装方法，禁止外部直接调用）
  ↓
【5. 完成】
  ├─ 保存对话到历史记录
  └─ 完成
```

### 关键特性

1. **智能意图识别**: LLM 理解用户真实意图，自动选择 Skill
2. **多步骤编排**: 复杂任务分解为有序步骤，数据自动流转
3. **知识库增强**: 二次分析时注入相关知识，提升准确性
4. **失败回退**: 意图识别失败或 Skill 执行出错时，自动转为普通 AI 对话
5. **命令执行兜底**: CommandSkill 支持执行型命令（如 /back、/spawn），覆盖 Skill 缺口
6. **LLM 二次分析中间协调层**: LLMOutputCoordinator 统一调度分析+输出，支持流式/非流式自动切换
7. **AI 响应统一输出管线**: 支持 5 种载体（含 SIDEBAR）、5 种场景配置，MessageDispatcher 封装输出逻辑
8. **流式输出全场景覆盖**: 普通对话/技能结果/任务结果/挂机回调均支持流式，状态机防竞态
9. **SIDEBAR 自动分页**: 超过 15 行自动拆分多页，标题使用 ai_prefix，并发安全
10. **公屏广播强制 CHAT**: public_reply 时双通道输出（触发者私有载体 + 全体 CHAT 广播）
11. **思考消息动态配置**: `output.thinking_channel` 独立配置，不与场景配置联动

### 示例流程

```
用户: "我手上是什么?这个能卖多少钱?"
  ↓
【意图识别】→ 多步骤任务
  ├─ step_1: bukkit_api.get_player_hand_item
  └─ step_2: market_query.query_price (依赖 step_1)
  ↓
【执行技能】
  ├─ step_1 → "钻石剑"
  └─ step_2 → 价格 $500
  ↓
【二次分析 + 知识库增强】
  检索到知识库:
  - 服务器规则: 稀有武器价格上限 $1000
  - 钻石剑属于中等价值物品
  
  LLM 综合分析:
  "你手上是一把钻石剑，市场价 $500。
   根据服务器经济政策，这个价格合理，
   建议在市场中出售。"
  ↓
【返回结果】
```

## 📊 模式 3：插件命令模式（Agent 禁用）

插件命令模式是专为**第三方插件集成**设计的接口，设计理念与普通模式完全不同。

### 为什么插件命令模式不启用 Agent 能力？

1. **回调机制要求纯文本输出**
   ```java
   executeCallback(callbackCommand, fullResponse);
   //                          ^^^^^^^^^^^^
   //                          必须是 String 类型！
   ```
   - Agent 路径可能返回结构化数据（Map、List 等）
   - 无法保证最终结果是可序列化的纯文本
   - 回调命令需要明确的文本内容作为参数

2. **职责定位不同**
   - ChatListener/KilacraftCommand: "帮我做点什么"（任务执行）
   - 插件命令: "给我一段 AI 生成的文本"（内容创作）

3. **性能考虑**
   - 插件命令可能被高频调用（如 MythicMobs 占位符）
   - 避免不必要的意图识别开销（~2-5秒）
   - 直接调用普通 AI 更快（~1-3秒）

4. **语义清晰**
   - `/kila plugins default 你好 UUID` = "用 default 人格回答'你好'"
   - 不是 "帮我执行某个任务"

### 完整调用链路

```
控制台: "/kila plugins default 你好 UUID callback_cmd"
  ↓
【1. 入口层】KilacraftCommand.handlePluginsCommand()
  ├─ 验证参数（人格、UUID、回调命令）
  ├─ 检查世界限制和冷却时间
  ├─ 获取隔离的历史记录 (UUID_人格)
  └─ 创建 PluginCommandResponseHandler
  ↓
【2. 人格化配置】
  ├─ 从 personalities.yml 加载人格提示词
  ├─ 替换 {player} 占位符
  └─ 构建完整的 system prompt
  ↓
【3. 普通 AI 对话】LLMProvider.processRequestWithCustomSystemPrompt()
  ├─ 【知识库检索】(在 GenericLLMProvider 内部)
  │   ├─ 检索相关知识片段
  │   └─ 注入到用户消息中
  ├─ 构建请求:
  │   ├─ system: 人格提示词
  │   ├─ history: 隔离的历史记录
  │   └─ user: 用户消息 + 知识库上下文
  ├─ 调用 LLM API (流式响应)
  └─ 返回纯文本回复
  ↓
【4. 回调层】
  ├─ 保存对话到隔离的历史记录
  ├─ 缓存最新回复 (供轮询获取)
  ├─ 执行回调命令:
  │   ├─ 替换 {response} 占位符
  │   ├─ 在主线程执行命令
  │   └─ 超时保护 (默认 3 秒)
  └─ 清理缓存
  ↓
【5. 完成】
```

### 关键特性

1. **纯文本输出**: 保证回调命令能正确接收和处理
2. **人格化**: 使用指定的人格提示词，风格可控
3. **知识库支持**: 仍然可以检索知识库，增强回答质量
4. **隔离历史**: 每个 `UUID_人格` 组合独立的历史记录
5. **回调机制**: AI 完成后自动执行指定命令

### 典型应用场景

**场景 1: MythicMobs 占位符集成**
```yaml
# MythicMobs 配置
Skills:
  BossSkill:
    Skills:
      - message{msg=%kilacraft_ai_answer(请问如何打败我?)%}
```

期望输出:
```
AI: "攻击我的弱点在头部，使用弓箭远程攻击，
     注意躲避我的火焰技能！"
```

**场景 2: 其他插件代码集成**
```java
// 某插件代码
String aiAdvice = plugin.callAI(playerUUID, "这个Boss怎么打?");
player.sendMessage(aiAdvice); // 显示文本建议
```

期望输出:
```
AI: "这个 Boss 有 3 个阶段，第一阶段...
     建议使用火焰抗性药水..."
```

**场景 3: 自动化脚本**
```bash
# 定时任务
/kila plugins daily_tips 今天有什么活动? UUID save_to_file
```

期望输出:
```
AI: "今天的活动有：
     1. 14:00 PVP 大赛
     2. 20:00 建筑比赛
     欢迎参加！"
```

## 🔍 核心差异对比表

| 维度 | ChatListener / Command | 插件命令模式 |
|------|----------------------|-------------|
| **触发方式** | 玩家聊天 / 控制台命令 | 控制台命令 (仅供插件调用) |
| **Agent 能力** | ✅ 启用 (意图识别 + Skill 执行) | ❌ 禁用 (直接普通 AI) |
| **意图识别** | ✅ LLM 自动识别 | ❌ 跳过 |
| **Skill 执行** | ✅ 支持单意图/多步骤 | ❌ 不支持 |
| **知识库检索** | ✅ 二次分析时注入 | ✅ 普通对话时注入 |
| **LLM 协调器** | ✅ LLMOutputCoordinator 统一调度 | ❌ 不支持 |
| **输出管线** | ✅ AIResponsePipeline（5种载体） | ❌ 直接输出 |
| **流式输出** | ✅ 全场景支持（状态机防竞态） | ❌ 不支持 |
| **人格系统** | ❌ 不支持 (仅默认系统提示词) | ✅ 必须 (可指定任意人格) |
| **输出形式** | 多样化 (Skill 结果 + AI 总结) | 纯文本 (必须可序列化) |
| **回调机制** | ❌ 不需要 | ✅ 必须 (传给调用方) |
| **历史记录** | 按玩家 UUID 隔离 | 按 `UUID_人格` 组合隔离 |
| **冷却时间** | 通用 cooldown_seconds | 专用 plugins_cooldown_seconds |
| **响应速度** | ~2-8秒 (含 LLM 意图识别+Skill) | ~1-3秒 (直接 AI) |
| **适用场景** | 玩家交互、任务执行 | 内容生成、插件集成 |

## 💡 设计哲学总结

### ChatListener / KilacraftCommand 模式

> "让玩家用最自然的方式与服务器交互，AI 理解意图并执行任务"

- 面向终端玩家
- 强调智能化和自动化
- 支持复杂的任务编排
- 输出灵活多样（5 种载体可选）
- 流式输出实时显示
- LLM 协调器统一调度

### 插件命令模式

> "为第三方插件提供稳定可靠的 AI 文本生成接口"

- 面向开发者
- 强调稳定性和可预测性
- 输出必须是纯文本
- 支持回调机制
- 不使用输出管线（直接输出）

### 为什么这样设计？

1. **职责分离**: 两种模式服务于不同的目标群体
2. **性能优化**: 插件集成不需要意图识别的开销
3. **可靠性**: 纯文本输出保证回调机制的稳定性
4. **灵活性**: 保留两种模式，满足不同需求

## 🎯 如何选择使用哪种模式？

### 使用 ChatListener / KilacraftCommand，如果：

- ✅ 玩家需要与 AI 进行智能交互
- ✅ 需要执行服务器操作（查询、购买、管理等）
- ✅ 希望 AI 理解复杂的多步骤任务
- ✅ 输出可以是多样化的（数据 + 建议）

### 使用插件命令模式，如果：

- ✅ 你是插件开发者，需要在代码中调用 AI
- ✅ 只需要 AI 生成的文本内容
- ✅ 需要将 AI 回复传递给其他系统
- ✅ 需要人格化的回复风格
- ✅ 需要回调机制实现自动化流程

## 🆕 v2.0.0 新增子系统架构

v2.0.0 引入了 6 个全新子系统，与原有架构并行运行：

### 1. 数据库持久化层

```
DatabaseManager (HikariCP 连接池)
  ├── H2Provider (嵌入式，零配置)
  ├── MySQLProvider (外挂，多子服共享)
  └── SchemaManager (自动迁移，H2/MySQL 双方言)
```

- 零配置开箱即用（默认 H2），同时支持 MySQL
- `/kila reload` 支持热切换数据库类型
- 失败自动回退旧连接池

### 2. 对话历史持久化

```
玩家消息 → 内存队列 → 30s 批量刷盘 → kca_conversation 表
                        ↑ 阈值触发(≥20条)
玩家下线 → 立即 flush
首次发言 → 懒加载历史 → 注入上下文
过期数据 → DataCleanupService 定时清理
```

### 3. 玩家画像系统

```
玩家登录/退出 → 三重门控检查 → LLM 画像分析 → kca_player_profile 表
                   ↑
          时间间隔 + 消息数 + 滑动窗口
画像八维度：游戏风格/性格特征/兴趣偏好/交互禁忌/回复偏好/空间记忆/已知事实/特别观察
画像摘要 → 动态注入 AI 系统提示词
```

### 4. 社交关系图谱

```
交互来源 → SocialGraph 加权增强 → kca_social_relation 表
  ├── 私聊 +0.01
  ├── TPA 传送 +0.02
  └── Skill 交互 +0.005

每日衰减（5%）→ 弱关系清理
水位标记 + DB SELECT FOR UPDATE（分布式安全）
社交关系提取器 → 定期扫描 kca_skill_log → 自动增强关系
```

### 5. 服务器事件采集

```
Bukkit 事件 → EventCollector → kca_server_event 表
  ├── 玩家死亡/成就/升级
  └── 市场交易（卖家视角）

离线事件聚合器 → 玩家登录时生成回顾摘要 → 注入问候语
```

### 6. 统一定时任务调度器

```
TaskScheduler (CAS 互斥保护)
  ├── 对话刷盘 (30s)
  ├── 数据清理 (可配置)
  ├── 社交关系衰减 (每日)
  ├── 社交关系提取 (定期)
  └── 画像分析触发 (登录/退出时)

/kila tasks → 查看所有托管任务运行状态
```

### 7. AI 登录问候系统

```
PlayerJoinEvent → LoginGreetingHandler
  ├── 首次登录 → 欢迎新玩家
  ├── 回归登录 → 三大分类数据聚合
  │     ├── 分类一：玩家自己的离线事件（死亡/成就/等级/市场）
  │     ├── 分类二：好友离线期间的动态（JOIN player_profile 获取名称）
  │     └── 分类三：摘要统计（累计时长/登录次数/上次亮点）
  └── 冷却检查 (greeting.yml)
       ↓
  GreetingPromptBuilder → LLM → AIResponsePipeline
```

## 🆕 v2.1.0 新增服主管理子系统架构

v2.1.0 引入了服主管理子系统，面向服务器运维场景，包含健康监控、玩家分析和审计日志三大模块。

### 1. 服主管理 Skill 注册体系

```
initializeAdminSystem()
  ├── AdminConfigManager (admin.yml 配置管理)
  ├── NotificationService (外部通知服务初始化)
  ├── AdminListener (事件监听，掉线中断采样)
  │
  ├── Admin Skill 注册 (始终注册，不依赖 API key / Spark)
  │   ├── ServerHealthSkill (3 action: alert_history / list_reports / read_report)
  │   ├── PlayerAnalysisSkill (6 action: online_trend / top_active / new_players /
  │   │                          profile_coverage / social_insights / player_relations)
  │   └── AuditLogSkill (3 action: query_logs / skill_stats / error_logs)
  │
  └── 守护线程创建 (三重门控)
      ├── 门控 1: databaseManager != null
      ├── 门控 2: admin.yml guardian.enabled + 推理模型 API 已配置
      ├── 门控 3: Spark 插件可用 (支持 2 分钟延迟重试)
      └── 全部通过 → 注册 ServerHealthGuardian 到 TaskScheduler
```

**关键设计**：
- 12 个 Admin Skill action 始终注册，无需 API key 即可使用查询功能
- 仅守护线程（自动监控）和 AI 智能诊断需要推理模型 API key + Spark
- Spark 不可用时支持延迟 2 分钟重试（兼容 Leaf 等延迟注册 Spark 的服务端）

### 2. 健康守护线程与 AI 诊断

```
ServerHealthGuardian (守护线程，每 10s 轮询)
  ├── SparkDataCollector (读取 TPS / MSPT / CPU)
  ├── 指标超过阈值 → 自动触发诊断
  │   ├── 防抖机制: 告警冷却 + 滑动窗口频率限制
  │   ├── Spark Profiler 采样 (auto 模式，全时段)
  │   ├── DiagnosticReportGenerator (生成 Markdown 诊断报告)
  │   │   ├── 服务器状态概览 (TPS / MSPT / 内存 / CPU)
  │   │   ├── 插件耗时排行 (self time 算法)
  │   │   ├── 热点方法触发路径
  │   │   ├── 玩家活动指标 (移动距离 / 分布)
  │   │   ├── 自监控文本 (Kilacraft-AI 自身资源占用)
  │   │   └── 保存到 plugins/Kilacraft-AI/reports/
  │   ├── 推理模型深度分析 (ThinkingModelConfig)
  │   └── 外部通知推送 (Discord / 钉钉)
  └── 采样完成后 → 报告文件 + 通知推送 + 数据库告警记录
```

**手动采样** (服主主动排查)：
```
/kila profile start [30-120]   → 启动采样
/kila profile status           → 查看状态
/kila profile stop             → 中断并丢弃
```

### 3. 外部通知推送

```
NotificationService
  ├── Discord Webhook
  │   ├── Embed 卡片消息
  │   └── 含告警原因 / 实时快照 / AI 诊断摘要
  └── 钉钉群机器人
      ├── Markdown 文本
      └── 可选 HMAC-SHA256 签名安全加固

/kila notify test → 测试通知渠道
```

**推送策略**：仅推送告警摘要，不含完整诊断报告附件，避免敏感信息泄露。

### 4. AdminSkillUtil 通用格式化层

```
AdminSkillUtil (静态工具类)
  ├── formatTimestamp()     → epoch → yyyy-MM-dd HH:mm
  ├── resolvePlayerName()   → UUID → 玩家名 (在线缓存 + DB 二级策略)
  ├── formatStrengthLevel() → 数值 → 语义化等级 (陌生/点头之交/普通朋友/好友/密友)
  ├── translateEventType()  → 事件枚举 → 中文可读标签
  ├── parseTimeRange()      → 自然语言时间范围 → epoch 时间戳
  └── executeAsync()        → 统一异步执行 + 异常隔离
```

**设计原则**：所有 Admin Skill 的 message 输出必须格式化，确保 AI 二次分析输入可读。

## 🆕 v2.2.0 新增子系统架构

v2.2.0 是一次大版本升级，新增了 **AI 主动层 + 联网能力 + 玩家自定义监听 + 对话推荐 + LLM 预算治理**五大子系统。这些子系统与玩家请求流水线（模式 1&2）相对独立，但共享 LLM 调用与输出管线。

### 1. 守护系统（Guardian，AI 主动看护）

守护系统是 AI 的**主动层**——不再"你问才答"，而是主动在玩家非即时感知的时机发声。与玩家请求流水线完全独立。

```
GuardianManager (生命周期 + 调度，opt-in 内存态，不持久化)
  ├── /kila guardian on → 启用默认套餐（3 个内置 monitor，硬编码不可配置）
  │     ├── BuiltInMonitors.createDefaultPollingMonitors() → 2 个轮询型
  │     │     ├── _inventory_near_full（背包空格 ≤ 6，每 600 tick 轮询）
  │     │     └── _low_durability（装备耐久 ≤ 5%，每 600 tick 轮询）
  │     └── BuiltInMonitors.createEventMonitors() → 1 个事件型
  │           └── _threat_target（监听 EntityTargetEvent，敌对生物锁定玩家）
  │
  └── GuardianEngine (事件驱动 + 心跳驱动评估)
        ├── 事件型 monitor：Bukkit 事件命中 filter → 求值 triggerPredicate（边沿触发）
        ├── 轮询型 monitor：心跳按 cadenceTicks 驱动 eval
        ├── 谓词层零 LLM（纯函数判定 PlayerState → bool）
        ├── 命中 → GuardianLlmAction（LLM 生成自然口语提醒）
        └── 已感知抑制：玩家打开任何物品界面时跳过背包/耐久告警
```

**关键设计约束**：
- **价值轴**：只在玩家"当下没盯着、但事后会在意"的时机发声（背包快满、装备耐久、视野外威胁）。饥饿/血量/氧气等 HUD 可感知的不做；苦力怕点燃（1.5s）等窗口短于 LLM 延迟的不做。
- **挂机暂停**：`PlayerActivityTracker` 判定挂机（默认 5 分钟无操作），挂机时 `tickPlayer` + `submitSignal` 双入口跳过 eval。
- **防刷屏**：每个 monitor 自带 `cooldownMillis`，冷却内不重复触发；动作失败（离线/关守护/LLM 失败）一律视为本轮没触发。
- **输出载体**：守护提醒默认走 `ACTION_BAR`（不刷屏主聊天），经 `LLMOutputCoordinator.outputAnalysisResult(... GUARDIAN ...)` 统一输出。
- **无治理层**：无告警优先级/分类/静音功能。玩家不想被骚扰直接关守护。GuardianSkill 只有 enable/disable/status 三个 action。

### 2. 玩家自定义监听（WatchSkill）

玩家用自然语言设定条件/事件监听（"盯铁锭到 64 个""BOSS 刷新提醒我"），独立于守护系统。

```
WatchSkill (AI 技能，skill_name=watch)
  ├── create_watch / cancel_watch / list_watches
  └── WatchService (内存态，不持久化)
        ├── 轮询型（POLLING）：定时执行内置 skill 的只读 action 取值比较
        │     └── 同一玩家所有轮询监听合并为单个定时器
        ├── 事件型（EVENT）：PlayerWatchListener（全局单例 Listener）
        │     ├── 监听 11 种高价值 Bukkit 事件
        │     │     熔炉烧好/作物成熟/实体死亡/生成/玩家死亡/传送/升级/换世界/方块破坏/钓鱼/聊天
        │     └── eventType → Set<WatchRef> 反向索引（无人订阅时零成本）
        └── 命中 → LLMOutputCoordinator.outputAnalysisResult（只通知 AI，不执行回调）

  每玩家上限：轮询 ≤ 3 / 事件 ≤ 5 / 全局 200
  下线延迟删除窗口（offlineGraceMinutes，默认 5 分钟，便于重连恢复）
  事件归属：玩家自身(O(1)) / 击杀者归属 / 坐标距离（基于创建时快照位置）
  冷却：AtomicLong CAS（Watch.casFireTime），并发事件下仅一个通过
```

> v2.2.0 移除了旧挂机任务系统（AFK Task），其能力被守护系统（默认套餐）+ WatchSkill（自定义监听）+ PlayerWatchSkill（跨玩家订阅）三个新系统替代。

### 3. 跨玩家上下线订阅（PlayerWatchSkill）

```
PlayerWatchSkill (AI 技能，skill_name=player_watch)
  ├── subscribe / unsubscribe / list / unsubscribe_all
  └── PlayerWatchService (内存订阅 + Bukkit Listener)
        ├── 订阅者下线自动清空（上限 5 个/玩家，硬编码）
        ├── 防乱序：下线通知取消尚未发出的上线通知
        └── 上线通知延迟 2 秒（等玩家完全进服）
  通知走统一 LLMOutputCoordinator.outputAnalysisResult(... GUARDIAN ...)
```

### 4. 联网搜索与网页抓取（WebSearch / WebFetch）

```
WebSearchSkill (skill_name=web_search, action=search)
  ├── web.yml 配置（provider: auto 按服务器语言路由）
  ├── 9 家供应商：国内 5（智谱/百度千帆/火山豆包/七牛百度/阿里IQS）+ 国际 4（Tavily/Brave/Exa/You.com）
  ├── 时间范围筛选（今天/最近一周/最近一月）
  └── 自动多步搜索（复杂问题拆成最多 5 个子搜索）

WebFetchSkill (skill_name=web_fetch, action=fetch，零配置)
  ├── 抓取网页正文 → AI 针对该页面回答问题
  └── SSRF 防护三件套（ssrf_protection: true 时生效）
        ├── IP 检查内嵌 DNS 解析（校验通过 IP = 实际连接 IP，防 DNS rebinding）
        ├── 响应体字节级硬限制（readBodyWithLimit，默认 2MB，防 OOM）
        └── 强制 HTTPS + 逐跳重定向复检（最多 3 跳，每跳重校验）
```

### 5. 对话推荐（Suggestion）

```
AI 回复完毕 → SuggestionService（仅在命令模式触发，连续对话模式不触发）
  ├── 基于多轮对话历史 + 当前可用技能摘要智能生成 1~5 个推荐问题
  ├── 强制"宁缺毋滥"（不确定就不输出）
  ├── /kila suggestion on|off|status（全体可用，opt-out）
  └── behavior.yml 的 suggestion 段配置（数量/超时/排除场景/排除技能/展示文案）
```

### 6. LLM 预算治理（LLMBudgetManager）

```
LLMOutputCoordinator 内含 LLMBudgetManager
  ├── 按玩家维度统计每小时调用次数
  ├── 超过阈值（budget_per_player_per_hour，默认 200）→ 触发 1 小时熔断
  ├── 二元熔断策略：
  │     ├── 玩家主动请求（聊天/技能/任务）→ 永不熔断，超预算也照常响应
  │     └── 被动调用（问候/推荐/守护/第三方回调）→ 熔断窗口内统一拒绝
  └── /kila reload 即时刷新阈值；设为 0 或负数完全禁用
```

**设计目标**：正常使用永远感知不到（200 次/小时正常达不到），只在异常工况（刷怪塔信号风暴、配置错误狂调、第三方插件失控）下兜底，优先保护玩家体验与服主的钱包。

### 7. Skill 注册总览

当前内置 17 个 Skill，分布在三个注册入口：

```
registerDefaultSkills() (KilacraftAI.java) — 8 个无条件 + 6 个条件
  ├── 无条件：GenericBukkitAPI / BukkitFX / Bukkit Stats / Utility
  │           ServerHealth / PlayerAnalysis / AuditLog / VersionInfo
  └── 条件：Command(config 开关) / MarketQuery+MarketAction(GMP) / CMI / WebSearch / WebFetch

initializeGuardianSystem()    → GuardianSkill
initializePlayerWatchSystem() → PlayerWatchSkill
initializeWatchSystem()       → WatchSkill
```

> 守护、玩家监听、跨玩家订阅三个 Skill 在各自子系统初始化时注册，而非 `registerDefaultSkills`。
