## 💡 核心理念：知识库质量决定一切

> **“Garbage In, Garbage Out”（垃圾进，垃圾出）**  
> —— George Fuechsel，计算机科学家

在 RAG（检索增强生成）技术中，**知识库文档的质量直接决定了检索质量和召回率**：

- ✅ **高质量知识库** → 精确检索 → 准确回答 → **节省 Token**
- ❌ **低质量知识库** → 混乱检索 → 错误回答 → **浪费 Token**

### 为什么质量影响 Token 消耗？

| 知识库质量 | 检索结果 | Token 消耗 | 回答质量 |
|----------|---------|-----------|--------|
| **高质量**（结构清晰、内容准确） | 1-2 个精确片段 | ~200-300 tokens | 准确、简洁 |
| **中等质量**（有结构但不够精确） | 3-5 个相关片段 | ~500-800 tokens | 基本准确 |
| **低质量**（混乱、重复、冗长） | 5+ 个噪声片段 | ~1000+ tokens | 可能错误 |

**结论**：花时间优化知识库文档，不仅能提高 AI 回答的准确性，还能**显著降低 API 调用成本**！

### 高质量知识库的关键特征

1. ✅ **结构清晰**：使用 Markdown 标题分级，便于智能分段
2. ✅ **内容精确**：每个章节聚焦一个主题，避免内容混杂
3. ✅ **语言简洁**：用简洁的语言表达，避免冗长啰嗦
4. ✅ **关键词丰富**：包含用户可能使用的关键词和同义词
5. ✅ **格式规范**：使用列表、表格等结构化内容
6. ✅ **定期维护**：及时更新过时内容，删除冗余信息

## 📖 概述

### 什么是知识库增强？

知识库增强（RAG - Retrieval Augmented Generation）是一种让 AI 能够访问**你的服务器专属知识**的技术。

**工作原理**：
```
用户提问 → 检索相关知识片段 → 将知识注入提示词 → LLM 生成回答
```

**传统 AI vs 知识库增强 AI**：

| 特性 | 传统 AI | 知识库增强 AI |
|------|---------|--------------|
| 知识来源 | 训练数据（通用） | 你的服务器文档 + 训练数据 |
| 准确性 | 可能过时或不准确 | 基于最新服务器规则 |
| 定制化 | 无法了解你的服务器 | 完全了解你的服务器 |
| 维护成本 | 需重新训练模型 | 只需更新文档 |

## 🔍 检索机制详解

### 智能分段算法

Kilacraft-AI 使用**三层降级分段策略**，自动选择最适合的分段方式：

```
策略 1: 按 Markdown 标题分割（优先）
  ↓ 如果没有标题
策略 2: 按段落分割（空行分隔）
  ↓ 如果没有空行
策略 3: 按固定大小分割（兜底）
```

---

#### 策略 1：按 Markdown 标题分割 ⭐ **推荐**

**触发条件**：文档中包含 `#` 到 `######` 标题

**分段规则**：
- 从标题开始，读取后续内容
- 遇到**空行**或**下一个标题**时停止
- 包含标题 + 紧跟的内容（不含空行后的内容）
- 如果单个片段超过 `max_size (500字符)` → 自动降级为策略 2

**案例 1：标准命令文档**

```markdown
# 服务器命令

## /back - 返回死亡点
当你死亡后，可以使用此命令快速回到死亡位置。
这在探索洞穴、打boss时非常有用。
冷却时间：30秒
权限：无

## /spawn - 传送回主城
传送回服务器的主城区域。
所有玩家都可以使用。
```

**分段结果**：
```
片段 1: "# 服务器命令" (10字符)
片段 2: "## /back - 返回死亡点\n当你死亡后...冷却时间：30秒\n权限：无" (80字符) ✅
片段 3: "## /spawn - 传送回主城\n传送回服务器...所有玩家都可以使用。" (70字符) ✅
```

**✅ 优势**：
- 每个命令保持完整上下文
- 标题信息保留（BM25 标题加权 +15 分）
- 语义完整性最好

---

**案例 2：超长命令说明（>500字符）**

```markdown
## /back - 返回死亡点
当你死亡后，可以使用此命令快速回到死亡位置。
这在探索洞穴、打boss时非常有用。
（中间省略 400 字符详细说明...）
注意事项：
1. 冷却时间 30 秒
2. 战斗状态无法使用
3. 需要站立不动 3 秒
```

**分段结果**：
```
策略 1 尝试：单个片段 600 字符 > max_size (500)
  ↓ 触发策略 2
策略 2 按段落分割：
  片段 1: "## /back - 返回死亡点\n当你死亡后..." (约 300 字符) ✅
  片段 2: "注意事项：\n1. 冷却时间 30 秒..." (约 200 字符) ✅
```

**⚠️ 注意**：
- 标题只在片段 1，片段 2 失去标题加权
- 用户搜索"back 冷却时间"可能匹配到片段 2，但没有标题加分

---

#### 策略 2：按段落分割 📄 **备选**

**触发条件**：Markdown 分割失败或文档无标题

**分段规则**：
- 以**空行**（`\n\n`）作为分隔符
- 每个段落必须 `≥ min_size (20字符)`
- 小于 20 字符的段落会被**过滤掉**

**案例 3：TXT 格式命令文档（有空行）**

```txt
/back - 返回死亡点
当你死亡后，可以使用此命令。
冷却时间：30秒

/spawn - 传送回主城
传送回服务器的主城区域。
所有玩家都可以使用。
```

**分段结果**：
```
片段 1: "/back - 返回死亡点\n当你死亡后...冷却时间：30秒" (60字符) ✅
片段 2: "/spawn - 传送回主城\n传送回服务器...所有玩家都可以使用。" (70字符) ✅
```

**✅ 优势**：
- 按空行自然分段
- 保持命令完整性

**⚠️ 注意**：
- 没有标题标记 → 失去 BM25 标题加权（-15 分）
- 命令名在普通文本中，权重较低

---

**案例 4：TXT 格式命令文档（无空行）** ❌ **严重问题**

```txt
/back - 返回死亡点
当你死亡后，可以使用此命令。
冷却时间：30秒
/spawn - 传送回主城
传送回服务器的主城区域。
/home - 回家
传送到你设置的家。
```

**分段结果**：
```
策略 1：无 # 标题 → 失败
策略 2：无空行 → 整个文档作为一个段落 (150字符)
  ↓ 150 < max_size (500)
  结果：1 个大片段包含所有命令 ❌
```

**❌ 问题**：
- 所有命令混在一起
- BM25 检索时无法区分
- 用户搜索"back"会返回包含所有命令的大片段

**✅ 正确做法**：命令之间必须加空行！

---

**案例 5：短命令列表（< 20字符）** ⚠️ **会被过滤**

```txt
/back 回死亡点

/spawn 回主城

/home 回家

/money 查余额
```

**分段结果**：
```
片段 1: "/back 回死亡点" (11字符) ❌ 小于 20 字符，被过滤
片段 2: "/spawn 回主城" (13字符) ❌ 小于 20 字符，被过滤
片段 3: "/home 回家" (9字符) ❌ 小于 20 字符，被过滤
片段 4: "/money 查余额" (13字符) ❌ 小于 20 字符，被过滤

结果：0 个片段 ❌ 所有命令都被过滤！
```

**⚠️ 重要说明**：
- `min_size: 20` 配置会过滤掉太短的片段
- **一行一个命令的简洁格式会被过滤！**
- 必须添加详细说明，使每个命令片段 ≥ 20 字符

**✅ 正确做法**：
```txt
/back - 返回死亡点
当你死亡后，使用此命令快速回到死亡位置。
冷却时间：30秒。

/spawn - 传送回主城
传送回服务器的主城区域，所有玩家都可以使用。
主城是安全区域，禁止PVP。
```

#### 策略 3：按固定大小分割 🔧 **兜底**

**触发条件**：段落分割也失败（无空行的连续文本）

**分段规则**：
- 每段最大 `max_size (500字符)`
- 优先在**句子边界**（`.` `!` `?` `\n`）切割
- 相邻片段有 `overlap (30字符)` 重叠

**案例 6：连续文本（无标题、无空行）**

```txt

```

**分段结果**：
```
策略 1：无标题 → 失败
策略 2：无空行 → 整个作为 1 段 (100字符)
策略 3：100 < max_size (500) → 不触发
结果：1 个片段 (100字符)
```

### 分段配置参数详解

```yaml
knowledge:
  segment:
    max_size: 500    # 单个片段最大字符数
    min_size: 20     # 单个片段最小字符数（小于此值会被过滤）
    overlap: 30      # 片段重叠字符数（仅策略3使用）
```

**参数说明**：

| 参数 | 作用 | 默认值 | 影响 |
|------|------|--------|------|
| `max_size` | 限制单个片段的最大长度 | 500 | 防止片段过长影响检索精度 |
| `min_size` | 过滤太短的无意义片段 | 20 | **⚠️ 短命令列表会被过滤！** |
| `overlap` | 保持相邻片段的上下文 | 30 | 仅策略3使用，避免信息丢失 |

**⚠️ `min_size` 重要提醒**：

如果你使用以下格式编写命令文档：

```txt
❌ 错误：一行一个命令（会被过滤）
/back 回死亡点
/spawn 回主城
/home 回家
```

必须改为：

```txt
✅ 正确：添加详细说明（≥ 20字符）
/back - 返回死亡点
当你死亡后，使用此命令快速回到死亡位置。
冷却时间：30秒。

/spawn - 传送回主城
传送回服务器的主城区域，所有玩家都可以使用。
```

或者使用 Markdown 格式：

```markdown
✅ 推荐：使用标题分段

当你死亡后，使用此命令快速回到死亡位置。

传送回服务器的主城区域，所有玩家都可以使用。
```

### 综合评分算法

当用户提问时,系统会对所有分段进行评分:

#### 级别 1：完整问题匹配（+50 加分）

系统直接拿玩家的**原始提问**（仅做小写化，不去分词、不去停用词、不抽取关键词）去比对每个片段。如果某个片段的正文**包含这整句原始提问**，给 +50 加分：

```
玩家提问: "圈地"  →  小写化后: "圈地"

匹配分段（正文里能找到完整的"圈地"二字）:
"""
## 如何圈地？

你可以使用 /claim 命令来圈定你的领地...
"""

得分: +50 分
```

**注意**：这个 +50 是对**玩家原始提问整体**做子串匹配，不是分词后再逐词匹配。因此：
- **短问题/单关键词**（如玩家直接说"圈地"）很容易命中，+50 加成明显。
- **长问题**（带"？""怎么"等完整句子，如"怎么圈地？"）几乎不会原样出现在任何知识片段的正文里，+50 通常不触发——此时靠的是下面级别 2/3 的逐词匹配。
- 所以"把核心概念词写进文档"比"原样抄玩家整句"更可靠（见下文标题加权、关键词评分）。

---

#### 级别 2：BM25 关键词评分

使用 HanLP TF-IDF 算法提取关键词，然后使用 BM25 公式计算每个关键词的匹配度：

```
用户提问: "我想建个农场，需要什么？"

关键词提取: ["农场", "需要"]

匹配分段:
"""
## 农场建造指南

建造农场需要准备：
1. 种子
2. 水
3. 工具
"""

```

**中文分词优化（v1.4.3 更新）**：
- **三层关键词提取策略**：原始查询 + 分词结果 + TF-IDF 关键词，兼容短文本和长文档
- **单字查询优化**：支持"弓"、"剑"等单字物品名查询，通过自定义词典和停用词检查
- **智能过滤停用词**：过滤"的"、"了"、"吗"等无意义词汇
- **TF-IDF自动提取重要关键词**：基于 HanLP 算法计算关键词权重
- **内置词汇表支持**：从 JAR 包的 internal/vocabulary/ 目录加载内置词汇，与自定义词汇合并自动去重

---

#### 级别 3：标题匹配（基础优先级）

如果内容和关键词都不匹配，则匹配标题：

```
用户提问: "规则是什么？"

匹配分段标题:
- "# 服务器规则" → 得分 50 分
- "## 基本规则" → 得分 45 分
```

---

**评分公式**：

#### 级别 1：完整问题匹配
- 如果分段内容包含完整用户问题：+50.0 分

#### 级别 2：BM25 关键词评分
```
基础分 = TF × (k1 + 1) / (TF + k1 × lengthNorm)
```

**BM25 公式组成部分**：
- **TF（词频）**：关键词在文档中出现的次数
- **IDF（逆文档频率）**：由 HanLP TF-IDF 自动计算
- **lengthNorm（文档长度归一化）**：`1 - b + b × (docLength / avgDocLength)`
- **k1（词频饱和参数）**：默认 1.5（建议 1.2-2.0）
- **b（文档长度归一化参数）**：默认 0.75（建议 0.5-0.8）

**计算公式**：
```
关键词得分 = TF × (k1 + 1) / (TF + k1 × lengthNorm)
```

**关键词权重**：
- 长度 ≥ 4：权重 3
- 长度 = 3：权重 2
- 长度 < 3：权重 1

#### 级别 3：位置加权
如果关键词出现在标题（以`#`开头的行）中：
```
关键词得分 += 15.0 × 关键词权重
```

#### 级别 4：精确匹配奖励
如果有任何关键词在文档中出现：
```
总分 += 10.0
```

#### 最终得分
```
总分 = 50.0 (完整匹配,如果有) 
    + 所有关键词的BM25得分
    + 所有标题加权的BM25得分
    + 10.0 (精确匹配奖励,如果有)
```

---

**示例计算**：

用户提问："圈地方法"
提取关键词：["圈地", "方法"]
文档片段：
```
## 如何圈地？

1. 准备 10 个金币
2. 站在想要圈地的位置
3. 执行 `/claim`
```

评分过程：
1. 完整问题匹配：× (不包含完整问题)
2. 关键词"圈地"（长度=2，权重=1）：
   - TF=3, 得分 = 3 × 1.5 / (3 + 1.5 × 0.6) = 2.25 × 1 = 2.25
3. 关键词"方法"（长度=2，权重=1）：
   - TF=2, 得分 = 2 × 1.5 / (2 + 1.5 × 0.6) = 1.5 × 1 = 1.5
4. 位置加权：检查"## 如何圈地？"是否包含"圈地"和"方法" → 只包含"圈地"
   - 标题中的关键词额外加分：+15.0 × 1 = +15.0
5. 精确匹配：√ (有任一关键词在文档中出现)
   
最终得分 ≈ 2.25 + 1.5 + 15.0 + 0 = 18.75

## ⚙️ 配置选项

### 配置文件位置

```
plugins/Kilacraft-AI/knowledge.yml
```

> 注：知识库的全部配置集中在独立的 `knowledge.yml` 中（早期版本曾放在 `config.yml`，已迁移）。修改后执行 `/kila knowledge reload` 或 `/kila reload` 生效；Embedding 相关项需重启。

### 相关配置项

```yaml
knowledge:
  enabled: true                    # 是否启用知识库
  max_relevant_chunks: 3           # 每次检索返回的最大片段数

  segment:
    max_size: 500                  # 每个片段最大字符数
    min_size: 20                   # 每个片段最小字符数（小于此值的片段会被过滤）
    overlap: 30                    # 片段重叠字符数（仅兜底分段策略使用）

  keywords:
    top_k: 10                      # 每次提取的关键词数量

  bm25:
    k1: 1.5                        # 词频饱和参数（建议 1.2-2.0）
    b: 0.75                        # 文档长度归一化参数（建议 0.5-0.8）
    avg_doc_length: 0              # 平均文档长度（0=启动时自动统计；填正数则用固定值）

  retrieval:
    noise_floor: 25.0              # 噪声地板：低于此分数的片段直接丢弃（硬阈值）
    relative_threshold: 0.3        # 相对阈值：低于「最高分 × 此比例」的片段丢弃（软阈值）
    rrf_k: 60                      # RRF 融合参数（仅开启 Embedding 时生效）

  embedding:
    enabled: false                 # 启用 Embedding 语义检索（需配置 api_url/api_key/model）
    api_url: ""                    # Embedding API 地址
    api_key: ""                    # API Key
    model: ""                      # 模型名（不同模型向量维度不兼容，修改需重启）
    dimensions: 1024               # 向量维度（须与所选模型一致）
    min_similarity: 0.5            # 最低余弦相似度阈值（建议 0.45~0.65）
    timeout_seconds: 10            # API 超时（秒）
    cache_enabled: true            # 向量缓存持久化（避免每次启动重算）

  custom_dictionary:
    enabled: true                  # 是否启用自定义词典
    words:                         # 中文自定义词（与内置词汇表、语料播种词合并去重）
      - "圈地"
      - "领地"
      - "红石"
    words_en: []                   # 英文自定义词
```

**最终过滤门槛**：`max(noise_floor, 最高分 × relative_threshold)`。这一两阶段过滤数学上保证：只要最高分片段超过了噪声地板，就**至少返回 1 条**相关结果，不会出现「明明有相关内容却返回空」的情况。

### 配置说明

#### `max_relevant_chunks`

控制每次检索返回的知识片段数量：

| 值 | 效果 | 适用场景 |
|----|------|---------|
| 1-2 | 精准回答 | 简单问题 |
| 3-5 | 平衡 | 大多数场景（推荐） |
| 6+ | 全面但冗长 | 复杂问题 |

**注意**：过多的片段会增加 token 消耗和响应时间。

---

#### `segment.max_size` / `min_size` / `overlap`

**详细说明请参考上面的“分段配置参数详解”章节**。

简要说明：
- `max_size`: 单个片段最大字符数（默认 500）
- `min_size`: 单个片段最小字符数（默认 20，**小于此值的片段会被过滤**）
- `overlap`: 片段重叠字符数（默认 30，仅策略 3 使用）

---

#### `keywords.top_k`

控制每次提取的关键词数量：

| 值 | 效果 |
|----|------|
| 5-10 | 平衡(推荐) |
| 10-15 | 更多召回,但可能引入噪音 |
| 15+ | 召回率高,但精确度下降 |

---

#### `bm25.k1` / `b` / `avg_doc_length`

BM25 算法参数：

| 参数 | 效果 | 建议值 |
|------|------|--------|
| k1 | 词频饱和点(越大越重视词频) | 1.2-2.0 |
| b | 文档长度归一化(越大越惩罚长文档) | 0.5-0.8 |
| avg_doc_length | 平均文档长度，用于长度归一化的分母 | 0（自动统计） |

- `avg_doc_length: 0`（默认）—— 启动时自动统计知识库所有片段的实际平均长度，BM25 对长短文档的评分更公平。
- 填一个正数则用固定值（适合知识库内容稳定、不想让它随语料变动的场景）。

> **IDF 权重补充**：BM25 的 IDF（逆文档频率）采用 `ln(1 + x)` 形式（BM25+ 变体），而非经典 `ln(x)`。前者保证 IDF 恒为正——出现在少数文档里的稀有、专业关键词排名更靠前，"玩家""命令"这类到处都有的通用词不会稀释结果；经典 `ln(x)` 在某词出现在超过半数文档时会变成负数，与外层「分数 > 0 才保留」的过滤冲突，本插件不采用。

---

#### `retrieval` - 检索过滤阈值（v2.1.2 重构）

旧版的单一硬阈值 `min_relevance_score`（默认 30）已被替换为**两阶段过滤**，避免「阈值设高了相关内容被误杀、设低了噪声涌入」的两难：

| 参数 | 默认 | 作用 |
|------|------|------|
| `noise_floor` | 25.0 | **噪声地板（硬门槛）**：绝对分数低于此值的片段直接丢弃，无论最高分多高 |
| `relative_threshold` | 0.3 | **相对阈值（软门槛）**：分数低于「当前最高分 × 此比例」的片段丢弃 |
| `rrf_k` | 60 | RRF 融合参数（仅开启 Embedding 时生效，见下文 Embedding 段） |

**最终门槛** = `max(noise_floor, 最高分 × relative_threshold)`。

调参方向：
- **想要更多结果**（弱相关问题也能答）：降低 `noise_floor`、降低 `relative_threshold`。
- **想要更严格**（答不上就沉默，避免误导）：调高两个值。
- 多数服主**保持默认即可**，默认值已能滤掉绝大多数噪声。

#### `embedding` - Embedding 语义检索（与 BM25 融合）

> ⚠️ **重要变更（v2.1.2 起）**：启用 Embedding 后**不再单独替换 BM25**，而是 **BM25 + Embedding 双路并行**，通过 **RRF（Reciprocal Rank Fusion，倒数排名融合）** 按排名融合结果。早期版本「配置 Embedding 后用语义检索替代 BM25」的描述已废止。

**为什么要融合而非替代**：BM25 擅长精确关键词匹配（命令名、专有名词），Embedding 擅长语义理解（同一概念的不同说法）。两路并行融合能兼顾两者优势——两条路都有贡献的片段排前面，只在一路出现的也能参与排序。

**工作原理（融合模式）**：
```
                ┌── BM25 路：关键词匹配 → 各片段 BM25 排名
用户查询 ───────┤
                └── Embedding 路：查询向量化 → 余弦相似度 → 各片段语义排名

RRF 融合：融合分 = Σ 1 / (rrf_k + 排名)    （两路排名各自贡献，rrf_k 默认 60）
          → 按融合分排序 → 取 Top-K
```

- `rrf_k` 越大，头部排名优势越平缓（更照顾靠后但两路都命中的片段）；越小，头部排名优势越明显。
- Embedding 路仅在 `embedding.enabled: true` 且配置了有效的 `api_url`/`api_key`/`model` 时启用；否则自动退化为纯 BM25（默认路径，绝大多数服主使用的模式）。

**配置示例**（`knowledge.yml`）：

```yaml
knowledge:
  embedding:
    enabled: true                                 # 启用 Embedding（须同时配 api_url/api_key/model，否则自动降级回纯 BM25）
    # 本插件用 api_url 指定供应商，没有 provider 字段
    api_url: "https://open.bigmodel.cn/api/paas/v4/embeddings"   # 修改后需重启
    api_key: "your-embedding-api-key"             # 修改后需重启
    model: "embedding-3"                          # 修改后需重启（不同模型向量不兼容）
    dimensions: 1024                              # 向量维度（embedding-3: 2048/1024/512/256；bge-large-zh/m3: 1024；text-embedding-3-small: 1536），修改后需重启
    min_similarity: 0.5                           # 最低余弦相似度阈值（0~1），建议范围 0.45~0.65
    timeout_seconds: 10                           # API 超时（秒），修改后需重启
    cache_enabled: true                           # 向量缓存持久化（避免每次启动重算）
```

**运维要点**：
- 向量缓存持久化（`cache_enabled: true`）：知识库分段的向量预计算并落盘，避免每次启动重新调用 Embedding API。
- 支持与对话 LLM 不同的 Embedding 供应商（智谱AI、硅基流动、OpenAI 等），只要兼容 OpenAI Embeddings 接口即可。
- 向量维度必须与所选模型一致，改维度或换模型需删除旧缓存后重启。
- **性能优化**：分段向量的范数（norm）会预计算缓存，余弦相似度运算量降低约 2/3；多名玩家同时提问时并发检索，不再互相串行等待。

**适用场景**：
- 知识库内容语义丰富，关键词匹配不够准确
- 用户查询表达方式多样（同一概念的不同说法）
- 期望更智能的语义理解而非关键词匹配

## 🐛 故障排除

### Q1: AI 没有使用知识库内容？

**检查清单**：

1. **确认知识库已启用**
   ```yaml
   knowledge:
     enabled: true
   ```

2. **确认文件已加载**
   ```
   /kila knowledge reload
   ```
   查看控制台输出：
   ```
   [Kilacraft-AI] 已加载 5 个知识文件，共 128 个分段
   ```

3. **检查文件格式**
   - 文件扩展名必须是 `.md` 或 `.txt`
   - 文件编码必须是 UTF-8

4. **调整返回片段数**
   ```yaml
   max_relevant_chunks: 5  # 增加返回数量
   ```

5. **开启调试模式**
   在 config.yml 中设置 `settings.debug_mode: true`
   查看检索日志，确认是否有匹配结果。

---

### Q2: 检索结果不准确？

**优化方法**：

1. **改进文档结构**
   - 使用清晰的标题
   - 添加关键词和同义词
   - 提供具体示例

2. **增加相关内容密度**
   ````
   ## 圈地/领地/保护
   
   圈地（领地、保护区域）是...
   
   相关命令：
   - /claim（圈地）
   - /unclaim（取消圈地）
   ```

3. **调整返回片段数**
   ```yaml
   max_relevant_chunks: 5  # 增加返回数量
   ```

4. **检查分段质量**
   开启调试模式，查看实际分段内容是否合理。

---

**优化方法**：

1. **减少知识库规模**

   - 控制单个文件大小

   知识库文件存储在 SSD 上可以显著提升读取速度。

## 圈地 / 领地 / 保护区域（Claim）
<!-- 标题含核心词 + 同义词。 -->
圈地（也叫领地、保护区域、Claim）用来保护你的建筑不被其他玩家破坏或窃取。
Q: 怎么圈地？ / 如何保护我的家？ / 领地怎么申请？

### 圈地步骤
1. 准备 10 金币
2. 站在要保护区域的中心
3. 输入 `/claim`

### 相关命令
- `/claim` —— 圈定领地
- `/unclaim` —— 取消领地
- `/trust <玩家>` —— 添加信任成员

## 死亡保护 / 返回死亡点
死亡后会掉落物品，但你可以在 30 秒内用 `/back` 返回死亡点捡回物品。
战斗中无法使用 `/back`，需要原地站立 3 秒。
Q: 死了怎么回去？ / 掉的东西能捡回来吗？ / back 冷却多久？

### 相关命令
- `/back` —— 返回上一个死亡点（冷却 30 秒）

## 🎯 如何编写高召回知识库文件（速查规则）

把检索系统的具体行为，翻译成"写文件时该怎么做"，按对召回率的影响从高到低排序：

| 排名 | 写法规则 | 背后的系统行为 | 代码位置 |
|---|---|---|---|
| 1 | 用 `##` / `###` 标题切分概念，**标题里放核心词 + 同义词** | 按 Markdown 标题切分；标题里的关键词额外加权 `+15×词权重`，多词可叠加 | `splitByMarkdownHeaders`、`calculateRelevance` |
| 2 | **标题与内容之间不要留空行** | 空行会切断标题块，把后续内容切成无标题孤立片段（失去标题加权、且可能 <20 字符被丢弃） | `splitByMarkdownHeaders` |
| 3 | 正文里也要出现核心词；命令名/专名写**全称** | BM25 词频得分（×词权重×5）+ 精确命中 `+10`；词越长权重越高（≥4→×3，=3→×2） | `calculateRelevance`、`BM25Scorer` |
| 4 | 同一概念把同义词/别名都写一遍 | 玩家换种说法也能命中关键词（提问会先分词再匹配） | `Chinese/EnglishTextProcessor.toSearchQuery` |
| 5 | 单个标题段控制在 **500 字符**以内，超了用 `###` 拆段 | 超过 `max_size` 会被二次切分，第二段起丢失标题加权 | `splitIntoChunks` |
| 6 | 每段内容 **≥ 20 字符** | 低于 `min_size` 的片段会被丢弃 | `splitByParagraphs`（`min_size:20`） |
| 7 | 命令/价格/步骤用列表或表格，**与标题紧挨、条目间不要空行** | 列表项无空行时同属一个标题块，整体召回；空行会切断 | `splitByMarkdownHeaders`（空行 = 切断边界） |
| 8 | 每条规则配 2~3 个玩家可能的问法（`Q:`） | 补关键词覆盖；短问题时原始提问可能整体命中 `+50` | `calculateRelevance` |
| 9 | 同一规则只写一次，不重复 | 重复会被当成两个片段召回，挤占 `max_relevant_chunks` 名额、可能矛盾 | `max_relevant_chunks` 限制 |

> **关于召回率的两条路**：
> - ① **写法优化**（上表）——付费维护知识库时的价值所在；
> - ② **检索引擎调优**（见 `wiki/已实施/知识库检索引擎增强设计文档.md`：BM25+Embedding 融合、可选重排、软阈值）。
>
> 重要：引擎优化**不改变分段/解析逻辑**（分段三策略、`min_size`/`max_size`、标题加权全部不变），所以**本表的写法规则在引擎优化前后都适用**——文件模板无需因引擎升级而改动。

## 🎬 场景范例：让 AI 执行自定义命令（命令技能）

当服务器有自定义命令（Essentials/CMI 等提供的 `/back`、`/home`、`/spawn`、`/tpa`、`/menu` 等），希望玩家用自然语言让 AI 代为执行时，把这些命令写进知识库，配合命令技能（技能名 `command`，类 `CommandSkill`）使用（需在 `config.yml` 开启 `command_skill.enabled: true`）。

**链路**：玩家说话 → Phase2 意图识别【检索知识库】→ 命中命令技能 + 提取 `command` 参数 → 以玩家身份执行。知识库的作用是教 Phase2 的 LLM 理解命令、生成正确的 `command`（不含 `/`）。命令技能是**兜底技能**，专用技能（经济/市场等）能完成的不写进来。

完整范例、设计要点与检查清单见独立文档 **《命令技能知识库编写范例.md》**。核心写法：

````markdown
# 服务器自定义命令清单

## 回到死亡点 / 返回刚才位置（/back）
`/back` 让你回到上一次所在的位置——通常是死亡掉落物品的地方。冷却 30 秒，战斗中不能使用。
Q: 我死了怎么回去捡东西 / 刚才掉的东西还能拿回来吗 / 送我回刚才那
AI 执行：back

## 回到自己的家（/home）
`/home` 直接传送回你设置的家。设了多个家时可在后面加家名，例如 `/home 主基地`。
Q: 回家 / 回我的基地 / 去我那个叫主基地的家
AI 执行：home（带家名时如 home 主基地）
````

**关键要点**：
- 命令名写 `/back` 全称 → 触发**语料播种**（`back` 进 HanLP 词典）+ 长词加权（×3）
- 标题堆**中文同义词**（回家/返回/死亡点）→ 中文召回主力，玩家说中文时靠它，语料播种管不到
- 每条配 `Q:` 玩家问法 + `AI 执行：xxx` 明确 command 值（不含 `/`）
- 带参数的命令务必给具体示例（如 `AI 执行：tpa Steve`）
- 只写服务器自定义命令，不写专用技能覆盖的需求
