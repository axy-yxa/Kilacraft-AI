# Kilacraft-AI - 数据库与持久化配置指南

> **最后更新**: 2026-08-04  
> **说明**: 本文档详细介绍 Kilacraft-AI 的数据库架构、持久化内容、配置方法和数据管理

---

## 📖 概述

v2.0.0 起 Kilacraft-AI 引入数据库持久化层，玩家对话、画像、社交关系等重要数据重启不丢失。同时支持 H2 嵌入式数据库和 MySQL 外挂数据库，可根据服务器规模和需求灵活选择。

### 核心特性

- ✅ **双数据库支持**：同时支持 H2 嵌入式数据库（零配置、单服友好）和 MySQL（多子服数据共享）
- ✅ **热切换数据库**：通过 `/kila reload` 即可在 H2 和 MySQL 间切换，失败自动回退
- ✅ **自动建表**：首次启动自动创建所有表结构（H2/MySQL 双方言兼容）
- ✅ **HikariCP 连接池**：高性能数据库连接池
- ✅ **异步写入**：所有写入操作异步执行，不阻塞主线程
- ✅ **定时清理**：过期数据可配置保留天数，自动清理

---

## 🚀 快速开始

### 选择数据库类型

Kilacraft-AI 同时支持两种数据库，根据你的服务器规模选择：

**H2 嵌入式数据库**（适合单服 / 开发测试）：  
零配置，开箱即用。首次启动自动在 `plugins/Kilacraft-AI/data/` 目录创建数据库文件，无需安装任何外部服务。

**MySQL 外挂数据库**（适合多子服 / 生产环境）：  
多子服间共享玩家数据。编辑 `plugins/Kilacraft-AI/database.yml`：

```yaml
type: MYSQL
mysql:
  host: localhost
  port: 3306
  database: kilacraft_ai
  username: root
  password: your-password
  table_prefix: "kca_"            # 表名前缀（仅允许字母/数字/下划线，含非法字符会回退默认值 kca_）

# 数据保留天数（见下方「配置参考」完整说明）
retention:
  conversation_retention_days: 60
  event_retention_days: 90
  skill_log_retention_days: 60
```

配置完成后执行 `/kila reload` 即可热切换，失败自动回退旧连接池。完整配置项见下方「配置参考」。

## 🗄️ 数据表结构

### kca_conversation - 对话历史

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT | 主键，自增 |
| `player_uuid` | VARCHAR(36) | 玩家 UUID |
| `role` | VARCHAR(16) | 角色（user/assistant） |
| `content` | TEXT | 消息内容 |
| `personality` | VARCHAR(32) | 人格标识（普通 AI 为空） |
| `source` | VARCHAR(16) | 来源标识（chat/command/plugin/greeting） |
| `created_at` | BIGINT | 消息创建时间戳（ms） |
| `server_id` | VARCHAR(64) | 服务器标识（群组服区分，单机服为空） |

**写入策略**：Write-Behind 异步刷盘  
**刷盘频率**：每 30 秒，或消息队列 ≥20 条时立即刷盘  
**读取策略**：玩家首次发言时懒加载最近 N 条历史

### kca_player_profile - 玩家画像

| 字段 | 类型 | 说明 |
|------|------|------|
| `uuid` | VARCHAR(36) | 玩家 UUID（主键） |
| `name` | VARCHAR(16) | 玩家名称 |
| `first_login` | BIGINT | 首次登录时间戳（ms） |
| `last_login` | BIGINT | 最近登录时间戳（ms） |
| `last_logout` | BIGINT | 最近登出时间戳（ms） |
| `login_count` | INT | 累计登录次数 |
| `total_playtime_ms` | BIGINT | 累计在线时长（ms） |
| `last_world` | VARCHAR(64) | 最近登出所在世界 |
| `last_x` | DOUBLE | 最近登出 X 坐标 |
| `last_y` | DOUBLE | 最近登出 Y 坐标 |
| `last_z` | DOUBLE | 最近登出 Z 坐标 |
| `last_greeting_time` | BIGINT | 最近 AI 问候时间戳（ms） |
| `profile_data` | TEXT | 画像 JSON（八维度） |
| `profile_analyzed_at` | BIGINT | 最近画像分析完成时间戳（ms） |
| `updated_at` | BIGINT | 最后更新时间戳（ms） |

**画像维度**：
- 游戏风格（playstyle）：PVP/PVE/建筑/探索/红石/生存等
- 性格特征（personality）：外向/内向/冒险/谨慎等
- 兴趣偏好（interests）：喜欢的领域和活动
- 交互禁忌（boundaries）：不喜欢的内容或行为
- 回复偏好（communication）：期望的 AI 回复方式
- 空间记忆（spatial）：提到的地点、基地位置
- 已知事实（facts）：玩家明确声明的事实
- 特别观察（notes）：LLM 自由发挥的个性化观察

> 画像摘要经 `GenericLLMProvider.buildDynamicContext()` 拼入 **user 消息**（非 system prompt），system 保持纯静态以最大化上下文缓存命中。

**分析触发条件**（三重门控，三者同时满足才触发）：
1. 距上次分析 ≥ 可配置时间间隔
2. 累计消息数 ≥ 阈值
3. 滑动窗口内有足够新消息

### kca_server_event - 服务器事件

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT | 主键，自增 |
| `event_type` | VARCHAR(32) | 事件类型 |
| `player_uuid` | VARCHAR(36) | 触发玩家 UUID |
| `target_uuid` | VARCHAR(36) | 目标玩家 UUID（可选） |
| `data` | TEXT | 事件附加数据 JSON |
| `created_at` | BIGINT | 事件时间戳（ms） |
| `server_id` | VARCHAR(64) | 服务器标识（群组服区分） |

**事件类型**（按来源分组）：

- **生命周期**：`PLAYER_LOGIN`、`PLAYER_LOGOUT`、`PLAYER_FIRST_JOIN`
- **市场**（GlobalMarketPlus 集成时采集）：`MARKET_ITEM_SOLD`、`MARKET_ITEM_LISTED`、`MARKET_MONEY_RECEIVED`
- **系统/管理**：`HEALTH_ALERT`、`HEALTH_ALERT_NOTIFIED`、`UPDATE_AVAILABLE`、`UPDATE_NOTIFIED`
- **玩家成就与行为**：`PLAYER_DEATH`、`PLAYER_ADVANCEMENT`、`PLAYER_LEVEL_UP`、`PLAYER_USE_TOTEM`、`PLAYER_DEFEAT_BOSS`、`PLAYER_COMPLETE_RAID`、`PLAYER_PET_DEATH`、`PLAYER_PVP_KILL`、`PLAYER_PVP_DEATH`、`PLAYER_TOOL_BREAK`、`PLAYER_CATCH_TREASURE`、`PLAYER_LIGHTNING_STRIKE`、`PLAYER_CURE_VILLAGER`、`PLAYER_MINE_ANCIENT_DEBRIS`、`PLAYER_TAME_ANIMAL`、`PLAYER_CRAFT_ENCH_GOLDEN_APPLE`、`PLAYER_BUILD_WITHER`
- **玩家自定义监听**：`PLAYER_WATCH_TRIGGERED`（玩家设定的监听条件命中时由监听系统写入）

> 注意命名细节：`PLAYER_LEVEL_UP`（带下划线，非 `PLAYER_LEVELUP`）、`MARKET_ITEM_SOLD`（非 `MARKET_SELL`）。另有 `ENTITY_PLAYER_LEVELUP` 是 Minecraft 音效名，与本事件无关，请勿混淆。

> **注意**：该表不存储 `player_name` 字段。当需要显示玩家名时（如 AI 问候中的好友动态），通过 LEFT JOIN `kca_player_profile` 表获取。此设计避免名称变更导致的数据不一致。

### kca_social_relation - 社交关系

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT | 主键，自增 |
| `player_uuid` | VARCHAR(36) | 玩家 UUID（关系持有方） |
| `target_uuid` | VARCHAR(36) | 目标 UUID（关系对象） |
| `relation_type` | VARCHAR(32) | 关系类型（如 PRIVATE_CHAT / TPA_INTERACTION / SKILL_INTERACTION） |
| `interaction_count` | INT | 交互次数 |
| `last_interaction` | BIGINT | 最近交互时间戳（ms） |
| `strength` | DOUBLE | 关系强度（每日衰减） |
| `updated_at` | BIGINT | 最后更新时间戳（ms） |

**交互权重**：
- 私聊：+0.01
- TPA 传送：+0.02
- Skill 交互（白名单 Skill）：+0.005

**衰减机制**：每日衰减 5%，强度低于阈值自动清理。

### kca_skill_log - 技能审计日志

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT | 主键，自增 |
| `player_uuid` | VARCHAR(36) | 触发玩家 UUID |
| `skill_name` | VARCHAR(32) | 技能名称 |
| `action` | VARCHAR(64) | 执行动作 |
| `entities` | TEXT | 涉及实体 JSON |
| `success` | BOOLEAN | 是否成功 |
| `result_message` | TEXT | 执行结果消息 |
| `trigger_message` | TEXT | 触发原文 |
| `execution_ms` | BIGINT | 执行耗时（ms） |
| `source` | VARCHAR(16) | 触发源（agent/manual） |
| `created_at` | BIGINT | 创建时间戳（ms） |
| `server_id` | VARCHAR(64) | 服务器标识（群组服区分） |

### kca_watermark - 水位标记（分布式互斥）

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | VARCHAR(64) | 水位名称（主键，如 `decay_date`、`extract_time:survival`） |
| `value` | VARCHAR(128) | 水位值（日期字符串或时间戳） |

用于分布式定时任务互斥（`SELECT FOR UPDATE` 行锁），保证群组服中只有一个子服执行清理/衰减等任务。水位名称自动跟随业务表策略：共享表使用全局水位名，隔离表的水位名带 `:server_id` 后缀。

### kca_profile_snapshot - 画像快照 `v2.0.2 新增`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT | 主键，自增 |
| `player_uuid` | VARCHAR(36) | 玩家 UUID |
| `snapshot_data` | TEXT | 画像快照 JSON（完整画像数据） |
| `message_count` | INT | 本次分析的消息条数 |
| `window_start` | BIGINT | 分析窗口起始时间（ms，= 上次 `profile_analyzed_at`，首次为 0） |
| `window_end` | BIGINT | 分析窗口截止时间（ms，≈ 当前时间） |
| `version` | INT | 画像版本号，对应 `profile_data` 中的 version 字段 |
| `analyzed_at` | BIGINT | 分析完成时间戳（ms） |

**设计说明**：
- **无 server_id**：与 `player_profile` 共享策略一致，天然跨服共享
- **无独立保留策略**：数据量极小（每玩家每天最多 1 条，受 `analysis_interval_days` 控制），永久保留，不纳入定时清理
- **追溯粒度**：`window_start + window_end + message_count` 精确追溯"第 N 版画像分析了哪段时间内的多少条消息"
- **触发时机**：每次画像分析完成后，与 `player_profile` 更新在同一 IO 任务中写入（同一个 Connection，同一个事务）

## 群组服数据隔离

### 表的隔离策略

| 表 | 策略 | 理由 | 有 server_id |
|---|:---:|------|:---:|
| `conversation` | 隔离 | 对话上下文属于子服 | 是 |
| `server_event` | 隔离 | 事件发生在具体子服 | 是 |
| `skill_log` | 隔离 | 技能执行在具体子服 | 是 |
| `player_profile` | 共享 | 玩家画像跨服累积（无 server_id 字段） | 否 |
| `social_relation` | 共享 | 社交关系天然跨服（无 server_id 字段） | 否 |
| `profile_snapshot` | 共享 | 画像快照与 player_profile 一致 `v2.0.2 新增` | 否 |
| `watermark` | 全局 | 分布式互斥锁，按任务名区分 | 否 |

> **注意**：player_profile、social_relation 和 profile_snapshot 天然共享——这些表没有 server_id 字段，所有子服操作同一份数据。watermark 表为全局表，水位名称按任务类型命名（如 `decay_date`、`cleanup_conversation`、`cleanup_events`、`extract_time:server_id`），不带 server_id 后缀的水位名表示全局只执行一次。

### 群组服配置方法

1. 每个子服的 `database.yml` 配置相同的 MySQL 连接参数
2. 为每个子服设置唯一的 `group.server_id`（如 `survival`、`minigame`、`rpg`）
3. 执行 `/kila reload` 即时生效

> **注意**：`server_id` 变更仅影响新写入的数据，已有数据不会自动迁移。

### 对话历史加载策略：settings.max_history

**settings.max_history（在 config.yml 中配置，非 database.yml）**：
取值范围 0-100（轮），超出自动钳制到边界值。
- 0：完全禁用历史（不保存、不加载）
- N：内存保留最近 N 轮（2N 条消息），DB 历史加载量 = N 条

> **画像八维度**：与早期版本的"五维度"（playstyle/personality/preferences/communication_style/notes）不同，当前版本扩展为八个字段。`analysis_system_prompt` 与 `incremental_system_prompt` 中的字段列表**必须保持一致**（八维度全列），否则增量分析可能漏写字段。修改任一提示词时，同步检查另一个。

## 🔧 操作指南

### 备份数据库

**H2 模式**：
直接备份 `plugins/Kilacraft-AI/data/` 目录下的 `.mv.db` 文件。

**MySQL 模式**：
使用 mysqldump 或你常用的数据库备份方案。

### 从 H2 迁移到 MySQL

1. 备份 `plugins/Kilacraft-AI/` 目录
2. 手动导出 H2 数据
3. 修改 `database.yml` 中的 `type` 为 `mysql`
4. 执行 `/kila reload` 使新配置生效

### 切换回 H2

1. 修改 `database.yml` 的 `type` 回 `h2`
2. 执行 `/kila reload`
3. 如切换失败，插件自动回退到旧连接池

## 🐛 常见问题

**Q: H2 数据库文件在哪里？**  
`plugins/Kilacraft-AI/data/kilacraft.mv.db`

**Q: 如何重置所有数据？**  
停止服务器，删除 `plugins/Kilacraft-AI/data/` 目录，重启即可。

**Q: MySQL 连接失败怎么办？**  
检查 `database.yml` 中的连接参数是否正确，MySQL 服务是否运行。切换失败时插件自动回退到旧连接池，不会丢失数据。

**Q: 清理间隔如何配置？**  
数据保留天数在 `database.yml` 的 `retention` 段按表分别配置：`conversation_retention_days`（对话，默认 60）、`event_retention_days`（事件，默认 90）、`skill_log_retention_days`（技能日志，默认 60）。值设为 `0` 表示永久保留。修改后执行 `/kila reload` 生效。清理任务由统一的定时调度器按固定周期执行（无需单独配置清理间隔）。
