# Kilacraft-AI 服主管理功能使用指南

> **最后更新**: 2026-08-01  
> **说明**: 本文档详细介绍 Kilacraft-AI 服主管理功能（服务器健康监控、玩家行为分析、审计日志查询）的完整使用方法、配置参考与场景示例

## 概述

Kilacraft-AI 的服主管理功能是一套专为 Minecraft 服务器管理员设计的智能监控与分析系统。它通过 AI 与 Spark 性能分析插件的深度集成，提供实时服务器健康监控、智能诊断、玩家行为分析等管理能力。

### 核心特点

1. **AI 驱动诊断**：使用推理模型进行深度分析，自动定位性能问题根因
2. **零配置自动监控**：守护线程 24/7 后台运行，异常自动检测与告警
3. **精准性能分析**：基于 Spark Profiler 的 self time 分析方法级热点，精确定位问题插件和触发路径
4. **自然语言交互**：无需记忆命令，直接用中文描述需求即可查询告警记录、玩家数据等

### 系统要求

- **推荐插件**：Spark（性能分析插件，软依赖）
- **推理模型**：在 `admin.yml` 的 `thinking_model` 段配置（API 地址/密钥/模型）。**未配置时自动回退使用 `llm.yml` 的基础对话模型**生成诊断报告（仅复用 url/key/model，`max_tokens`/`timeout` 仍用诊断专用值，避免报告被截断）——降低使用门槛，无需额外配置推理模型即可使用健康诊断。
- **完整依赖**：健康监控守护线程需要 **Spark + 推理模型（或回退的对话模型）配置** 同时满足才会启用；任一缺失时，守护线程不创建，但手动采样命令和历史告警查询仍可用（前提：Spark 可用）
- **服务器环境**：支持 Paper/Spigot 等主流服务端
- **网络要求**：服务器需可访问外网（用于 Spark Profiler 数据上传和推理模型 API 调用）

#### 内置 Spark 的服务端

以下服务端已内置 Spark，无需额外安装插件即可使用健康监控功能：

| 服务端 | 内置 Spark 起始版本 | 说明 |
|--------|---------------------|------|
| **Paper** | 1.21+ | Paper 官方从 1.21 起内置 Spark，替代已废弃的 Timings |
| **Folia** | 1.21+ | 基于 Paper，同步内置 Spark |
| **Purpur** | 1.19.1+ | 基于 Paper，较早内置 Spark |
| **Leaf** | 1.21+ | 基于 Paper/Gale 分支，继承内置 Spark |
| **Pufferfish** | 1.19+ | 基于 Paper，内置 Spark |

> **提示**：使用上述服务端时，直接配置推理模型 API 密钥即可启用完整健康监控功能。使用 Spigot 等未内置 Spark 的服务端，需手动安装 [Spark 插件](https://spark.lucko.me/)。

## 1. 服务器健康监控

### 1.1 监控指标与告警

守护线程每 10 秒轮询 Spark API 检测以下性能指标，任一超过阈值即触发告警：

| 指标 | 说明 | 正常范围 | 告警阈值 |
|------|------|----------|----------|
| **TPS** | 每秒游戏刻数（1 分钟窗口） | 20.0 | < 15 |
| **MSPT** | 每刻毫秒数（10 秒/1 分钟窗口） | < 50ms | 10 秒窗口 Max > 50ms（需连续 3 次确认）或 1 分钟窗口 P95 > 50ms |
| **CPU** | 进程 CPU 使用率（1 分钟窗口） | < 70% | > 80% |

告警触发后，守护线程自动启动 Spark Profiler 采样，完成后调用推理模型生成诊断报告。

#### 服务器活动指标（辅助诊断）

Spark Profiler 只能采样 CPU 活动，无法捕获磁盘 I/O、网络等非 CPU 瓶颈。为弥补此盲区，采样窗口内额外采集以下指标注入 AI 诊断提示词：

- **区块加载统计**：各世界在采样期间的区块加载次数，高区块加载增量 + 低 CPU 热点是磁盘 I/O 瓶颈的典型信号
- **玩家活动分布**：各世界在线玩家数量和进出变化，辅助判断性能压力来源

诊断报告中还会展示 GC 详情、内存使用、实体分布等元数据信息。

### 1.2 自动诊断

#### 工作流程

```
每10秒轮询 Spark API → 指标超阈值 → 启动 Profiler 采样（30秒）
    → 拉取采样数据 → 流式解析调用栈 → AI 推理模型诊断 → 生成报告 → 通知管理员
```

#### 防护机制

- **MSPT 连续确认**：MSPT max 使用 10 秒窗口检测，需连续 3 次超阈值才触发，有效过滤瞬时尖峰
- **统一冷却**：一次分析完成后，5 分钟内不重复触发新分析（不区分指标类型）
- **频率上限**：滑动时间窗口内限制自动分析次数（默认每小时最多 5 次），防止资源耗尽
- **互斥锁**：同一时间只有一个分析任务运行，新的告警不会打断正在进行的分析

### 1.3 手动性能采样

当需要主动排查问题时，使用手动诊断命令（需 Spark 插件可用）：

**启动性能采样：**
```bash
/kila profile start [秒数]
```
- **秒数**：采样时间，范围 30-120 秒，默认 60 秒
- 采样完成后自动生成诊断报告

**查看采样状态：**
```bash
/kila profile status
```

**中断采样并丢弃数据：**
```bash
/kila profile stop
```

> 手动采样时，若服主掉线，系统会自动中断采样。

### 1.4 诊断报告

#### 触发时机

1. **自动触发**：守护线程检测到性能异常时自动生成
2. **手动触发**：使用 `/kila profile start` 命令启动采样，完成后自动生成

#### 报告内容

- **§1. 服务器状态概览**：触发原因（仅自动模式）、TPS/MSPT/CPU/内存、在线玩家与实体统计、GC 详情
- **§2. 插件性能分析**：已安装插件耗时（快速定位问题插件）+ Top 热点方法触发路径（定位具体原因），所有百分比均为 self time
- **§3. AI 诊断结论**：问题根因分析、优化建议、具体解决方案

#### 报告文件

保存在 `plugins/Kilacraft-AI/reports/`，文件名格式 `health_report_{auto|manual}_YYYY-MM-DD_HH-mm-ss.md`（`auto` 为自动诊断，`manual` 为手动采样）。报告永久保存，不会自动删除。

### 1.5 告警通知

#### 游戏内通知

- **自动模式**：诊断完成后通知所有拥有 `kilacraft.admin.health` 权限的在线管理员
- **手动模式**：仅通知命令发起者

#### 外部通知（仅自动模式）

自动触发诊断成功后，可通过 Discord Webhook 或钉钉群机器人向外部平台推送告警通知。手动触发的诊断不会推送外部通知。

通知内容包含：触发指标和原因、实时性能快照（TPS/MSPT/CPU）、AI 诊断结论摘要。

> **注意**：推送内容不包含完整诊断报告附件，避免敏感信息（服务端版本、Spark URL、玩家名等）泄露到外部平台。完整报告请登录服务器查看。

**渠道能力对比：**

| 功能 | Discord | 钉钉 |
|------|---------|------|
| 消息类型 | Embed 卡片 | Markdown 文本 |
| 安全加固 | — | 可选 HMAC-SHA256 加签 |

> AI 诊断失败时不会推送外部通知（仅有错误信息，无诊断参考价值）。

**测试通知渠道：**
```bash
/kila notify test
```
向所有已配置的渠道发送测试消息，验证 webhook URL 和加签密钥是否正确。

### 1.6 历史告警查询与报告回顾

通过自然语言向 AI 助手查询历史告警记录和诊断报告：

#### 历史告警查询

**示例查询：**
- "过去一天服务器有什么告警？"
- "查看最近 3 天的健康告警记录"
- "TPS 低于 15 的告警有哪些？"

**返回信息：** 告警记录列表、按插件/指标/时间聚合的统计、最低 TPS 等关键指标。

#### 诊断报告回顾

AI 可以读取保存在服务器上的历史诊断报告文件，回顾完整的分析结论。

**示例查询：**
- "列出最近的诊断报告" — 返回报告文件列表（含时间、模式、文件大小）
- "查看上次自动诊断的报告" — 读取并展示完整报告内容（§1 状态概览 + §2 插件分析 + §3 AI 结论）
- "对比这两次报告的 TPS 和 MSPT 变化" — 连续读取多份报告后综合分析
- "这个月 MythicMobs 是不是一直有性能问题" — 先查告警统计定位可疑插件，再读具体报告确认

> AI 读取报告时会自动剥离推理过程的思考链（对机器无价值），仅保留最终诊断结论，因此响应更快。如果服主想查看完整推理过程，可直接在服务器 `plugins/Kilacraft-AI/reports/` 目录中打开报告文件。

## 2. 玩家行为分析

### 2.1 功能简介

通过自然语言查询，了解服务器的玩家生态：

- **在线趋势**：玩家登录/登出的时间分布
- **活跃排行**：最活跃的玩家排名
- **新玩家流入**：新玩家加入情况
- **画像覆盖**：AI 画像分析的覆盖率
- **社交洞察**：玩家社交网络分析
- **玩家关系**：查询指定玩家的社交关系详情（关系类型、强度等级、互动频率、最近互动时间）

### 2.2 使用方式

#### 在线人数趋势

**示例：** "过去一周玩家在线趋势怎么样？"

返回时间段内登录/登出次数，按小时或天聚合的趋势数据。

#### 活跃玩家排行

**示例：** "查看最活跃的玩家排行榜"

返回玩家登录次数排名、在线时长统计、最近登录时间。

#### 新玩家流入

**示例：** "过去一周有多少新玩家加入？"

返回新玩家加入数量、时间分布趋势。

#### 画像分析覆盖率

**示例：** "AI 画像分析覆盖了多少玩家？"

返回总玩家数量、已分析/待分析数量、覆盖率百分比。

#### 社交图谱洞察

**示例：** "查看玩家社交网络分析"

返回社交关系总数、平均关系强度、孤立玩家列表。

#### 指定玩家社交关系

**示例：** "查看玩家 Steve 的社交关系"、"Hub 有哪些好友"

返回指定玩家的社交关系列表，包括关系对象、关系类型、强度等级（陌生/点头之交/普通朋友/好友/密友）、互动次数、最近互动时间。

## 4. 配置指南

所有配置位于 `plugins/Kilacraft-AI/admin.yml`，支持 `/kila reload` 热重载（部分需重启守护线程的配置会自动处理）。

### 4.1 守护线程与告警阈值

```yaml
health_guardian:
  enabled: true                    # 是否启用守护线程
  interval_seconds: 10             # 轮询间隔（秒）
  cooldown_minutes: 5              # 分析后统一冷却期（分钟）
  auto_profiler_timeout: 30        # 自动模式采样时长（秒）
  max_auto_analysis_per_window: 5  # 滑动窗口内最大自动分析次数
  auto_analysis_window_minutes: 60 # 滑动窗口时长（分钟）
  mspt_consecutive_threshold: 3    # MSPT max 连续确认次数

  alerts:
    tps_threshold: 15              # TPS 1分钟窗口阈值
    mspt_max_threshold: 50         # MSPT 最大值阈值（毫秒，10秒窗口）
    mspt_p95_threshold: 50         # MSPT P95 阈值（毫秒，1分钟窗口）
    cpu_threshold: 80              # CPU 进程使用率阈值（百分比）
```

**根据服务器规模调整阈值：**

| 服务器规模 | TPS 阈值 | MSPT 阈值 | CPU 阈值 |
|------------|----------|-----------|----------|
| 小型（1-20 人） | 18 | 40 | 70 |
| 中型（20-100 人） | 15 | 50 | 80 |
| 大型（100+ 人） | 12 | 60 | 85 |

### 4.2 推理模型

```yaml
thinking_model:
  api_url: "https://api.deepseek.com/v1/chat/completions"
  api_key: "your-api-key"
  model: "deepseek-reasoner"
  max_tokens: 4096
  timeout_seconds: 120
```

**支持的推理模型：**

| 提供商 | 推荐模型 |
|--------|----------|
| DeepSeek | `deepseek-reasoner` |
| OpenAI | `o3`、`o4-mini`、`o1` |
| 硅基流动 | `deepseek-ai/DeepSeek-R1` |
| OpenRouter | `deepseek/deepseek-r1`、`openai/o3-mini` |
| Google Gemini | `gemini-2.5-flash-preview-05-20`（思考模式） |

### 4.3 外部通知

```yaml
notification:
  enabled: false                   # 是否启用外部通知
  channels:
    - type: discord                # Discord Webhook
      webhook_url: ""
    - type: dingtalk               # 钉钉群机器人
      webhook_url: ""
      secret: ""                   # 加签密钥（可选，建议开启）
```

### 4.4 采样策略与资源限制

**手动采样时长建议：**
- 日常监控：60 秒
- 问题排查：90-120 秒
- 性能测试：120 秒

**Profiler 数据保护：**
```yaml
health_guardian:
  max_profiler_download_bytes: 52428800  # 50MB 阈值
  download_when_exceeded: false          # 超过阈值是否继续下载
```

## 6. 使用场景示例

### 6.1 实时性能诊断

#### 场景 1：服务器出现卡顿，立即诊断

玩家反馈或自己感觉到服务器卡顿时，立即启动手动采样定位问题。

```bash
/kila profile start 90        # 常规排查：90 秒采样
/kila profile start 30        # 紧急场景：30 秒快速定位
```

采样完成后系统自动生成诊断报告，直接查看 §2（插件耗时 + 热点方法触发路径）定位卡顿原因，根据 §3 AI 建议采取措施。

#### 场景 2：间歇性 / 特定时段性能下降

对于不是持续出现、而是在特定条件下才触发的性能问题，有两种策略：

**策略 A：被动捕获（守护线程自动监控）**

确保 `health_guardian.enabled: true`，可适当降低告警阈值提高灵敏度。问题再次出现时，守护线程自动触发诊断并生成报告。

**策略 B：主动出击（在问题时段手动采样）**

在性能下降的时间段启动手动采样：`/kila profile start 120`，对比高峰期与非高峰期的报告定位瓶颈。

### 6.2 变更效果量化评估

> 利用 AI 报告读取能力（`list_reports` + `read_report`），AI 可读取历史诊断报告并智能对比，将“感觉好像快了”变成精确的量化评估。

#### 场景 3：插件安装 / 升级前后对比

**操作步骤：** 变更前启动采样生成基准报告 → 执行变更 → 变更后再次采样 → 让 AI 量化对比

**示例对话：**
- “我昨天升级了 MythicMobs，帮我看看性能有没有改善”
- AI 自动读取升级前后的两份报告，对比 §2 插件耗时占比和 §1 MSPT 变化
- AI 输出：“升级前 MythicMobs 占 12.3%，升级后降至 3.1%，MSPT P95 从 45ms 降至 15ms，改善明显”

#### 场景 4：服务器 / 配置变更效果验证

**操作步骤：** 与场景 3 相同，适用于服务端升级、JVM 参数调整、GC 配置优化等任何变更

**示例对话：**
- “我昨天调了 GC 参数，帮我看一下效果”
- AI 自动读取配置变更前后的报告，对比 §1 GC 详情
- AI 输出：“配置变更前 G1 Young GC 每分钟 4 次、均耗时 35ms，变更后每分钟 2 次、均耗时 18ms，GC 总耗时减少约 60%”

### 6.3 历史数据深度分析

> 以下场景利用 AI 的报告读取能力，实现之前做不到的深度洞察。

#### 场景 5：周期性卡顿规律挖掘

**示例对话：**
- “最近三天每天都会卡顿，帮我找找规律”
- AI 自动：`health_report` 获取告警分布 → 发现集中在晚上 20:00-22:00 → `list_reports` 列出该时段的报告 → 逐一 `read_report` 读取
- AI 输出：“三天共 4 次告警，均在 20:00-22:00 之间，共同特征：某区块实体堆积（掉落物 200+），疑似刷怪塔产物未自动清理”

#### 场景 6：特定插件长期影响追踪

**示例对话：**
- “MythicMobs 这个插件最近一个月是不是一直有性能问题？”
- AI 自动：`health_report` 过滤 plugin=MythicMobs → `read_report` 读取所有相关报告
- AI 输出：“过去 30 天共 8 次涉及 MythicMobs 的告警，主要集中在 5 月 10-15 日（占比 5-12%），升级后降至 1-3%，近两周已无相关告警，问题已解决”

#### 场景 7：跨时间段性能趋势分析

**示例对话：**
- “帮我对比上周和本周的服务器性能趋势”
- AI 自动按时间顺序读取多份报告，提取 TPS/MSPT/CPU/内存/GC 数据

## 7. 常见问题解答

### Q1: 为什么服务器健康监控功能不可用？

请检查以下条件（需同时满足）：
1. Spark 是否可用（Paper 1.21+/Folia/Purpur 等已内置，其他服务端需手动安装 Spark 插件）
2. `admin.yml` 中的推理模型 API 密钥是否已配置（不能为占位符 `your-api-key`）
3. 服务器是否能访问外网
4. `health_guardian.enabled` 是否为 `true`

### Q2: 诊断报告生成失败怎么办？

可能原因：API 密钥无效或额度不足、网络问题、Spark Profiler 数据过大。检查服务器日志获取详细错误信息，尝试增加 `timeout_seconds`。

### Q3: 如何清理历史诊断报告？

报告保存在 `plugins/Kilacraft-AI/reports/`，可手动删除或按时间筛选清理。

### Q4: 守护线程会影响服务器性能吗？

守护线程设计为轻量级：正常运行时仅内存轮询、零存储开销。仅在检测到异常时才触发 Profiler 分析，且有冷却和频率限制。

### Q5: 如何调整监控灵敏度？

在 `admin.yml` 中调整告警阈值：降低阈值更敏感，提高阈值更宽松。参考 §4.1 的按服务器规模建议。

### Q6: 外部通知没有收到怎么办？

1. 确认 `notification.enabled` 为 `true`
2. 检查各渠道的 `webhook_url` 是否填写完整
3. 如果使用钉钉加签，确认 `secret` 与机器人安全设置一致
4. 执行 `/kila notify test` 测试命令验证
5. 查看控制台日志，搜索 `[通知]` 前缀的错误信息
6. 注意：外部通知仅在**自动触发诊断成功**时推送，手动诊断不推送

### Q7: 守护线程不触发告警怎么办？

1. 检查 `admin.yml` 中的告警阈值是否设置过高
2. 确认推理模型 API 密钥已配置
3. 验证 Spark 插件是否正常运行
4. 注意冷却期机制：上次分析后 5 分钟内不会再次触发
5. MSPT 告警需连续 3 次超阈值，瞬时尖峰不会触发

### Q8: 如何查看系统日志排查问题？

关键日志标识：
- `[健康监控]`：守护线程、手动采样、诊断分析相关日志
- `[通知]`：外部通知相关日志

日志级别：INFO（正常操作）、WARN（需关注）、ERROR（需处理）。

## 8. 辅助诊断命令

除三大管理功能外，还有两个与服主管理强相关的通用命令：

### `/kila doctor` —— 配置自检

一键诊断插件配置与运行状态。游戏内输出采用**分组折叠摘要**格式：各组显示「X 正常, Y 警告, Z 异常」标题行，仅异常项展开详情，大幅减少健康时的聊天刷屏。控制台输出更详细（含脱敏的完整配置、缓存命中率、Web 搜索供应商状态等）。

检查项分组示例：数据库连接、LLM 连通、Spark、各项 AI 能力开关、**LLM 缓存命中率**（命中率 ≥50% 正常、≥30% 偏低、<30% 异常）、Web 搜索供应商状态等。需 `kilacraft.admin.info` 权限（默认 OP）。

> 注：可观测组中的 `health_guardian` 指服务器健康监控（即本文档的功能），与守护系统（Guardian，AI 主动看护）是两个不同概念，命名上已区分避免混淆。

### `/kila cache` —— LLM 缓存命中率统计

实时查看大模型提示词缓存的命中率和节省率，帮助判断 LLM 调用成本是否优化到位。按多种 AI 调用类型逐一展示（意图识别两阶段、二次分析、普通对话、守护、问候、画像、推荐、工具通知、服务器诊断等），每类显示请求数、输入 Token 消耗、缓存命中率与节省量。

- 自动兼容 DeepSeek（`prompt_cache_hit_tokens`）、OpenAI（`cached_tokens`）、Anthropic（`cache_read_input_tokens`）三家主流厂商的缓存上报字段，无需额外配置。
- 数据仅在当前服务器会话内存中累积，重启清零。
- `/kila cache reset` 手动重置统计。
- 需 `kilacraft.admin.cache` 权限（默认 OP）。
