# 意图识别提示词配置指南

## 📋 概述

意图识别提示词系统通过配置文件 `intent_prompts.yml` 定义 LLM 如何理解用户输入并识别技能意图。

**重要说明**: 
- **意图识别系统**专注于任务步骤编排与 Agent 能力的 Skill 选择
- **人格系统**是独立的功能,在插件命令模式下使用,通过 `personalities.yml` 配置不同人格的提示词
- 意图识别提示词**不包含**多个人格的配置,它只负责识别用户想要执行什么操作

## 📁 文件位置

```
plugins/Kilacraft-AI/
├── intent_prompts.yml          # 意图识别提示词配置文件
└── config.yml                  # 主配置文件
```

首次启动插件时会自动从 jar 包中复制默认的 `intent_prompts.yml` 到插件目录。

## 🔧 配置结构

配置文件采用 YAML 格式,分为 6 个主要部分 + 1 个输出格式规则:

### 1. 角色定义 (role_definition)

定义 AI 意图识别助手的身份和核心职责。

```yaml
role_definition: |
  你是一个智能的技能意图识别助手，专门分析用户在 Minecraft 游戏中的自然语言输入...
```

**作用**: 让 LLM 明确自己的任务边界和工作目标(意图识别、参数提取、任务分解)。

**注意**: 这里定义的是**意图识别助手**的角色,不是游戏 NPC 的人格。人格系统通过 `personalities.yml` 独立配置。

**优化建议**: 
- 保持简洁明了
- 突出核心职责(意图识别、参数提取、任务分解)
- 避免混入人格相关的描述

---

### 2. 输出格式强制要求 (output_format_rules)

定义 AI 输出 JSON 时的格式规范。

```yaml
output_format_rules: |
  【输出格式强制要求】
  1. **只返回纯 JSON 对象**，不要包含任何 Markdown 标记（如 ```json、```）
  2. **不要添加任何额外文本**，包括：识别理由说明、注释、解释、总结等
  3. **不要使用换行和缩进**，JSON 应该在一行内（便于解析）
  4. **严禁**在 JSON 后面添加任何文字说明
```

**作用**: 确保 LLM 输出的 JSON 可以被程序直接解析,避免格式错误。

**注意**: 这是独立的一级配置项,不属于 response_format。

---

### 3. 响应格式规范 (response_format)

定义三种标准响应格式的 JSON 模板。

#### 单意图格式 (single_intent)
用于简单、独立的单一操作。

```yaml
single_intent: |
  {
    "skill_name": "技能名称",
    "action": "具体动作",
    "entities": { "参数名": "参数值" },
    "confidence": 0.95,
    "reasoning": "识别理由说明"
  }
```

#### 无效意图格式 (invalid_intent)
当用户输入与任何技能无关时使用。

```yaml
invalid_intent: |
  {
    "skill_name": null,
    "action": null,
    "entities": {},
    "confidence": 0.0,
    "reasoning": "无法识别到相关技能的原因"
  }
```

#### 多步骤任务格式 (multi_step_task)
用于需要多个步骤协同完成的复杂任务。

```yaml
multi_step_task: |
  {
    "goal": "任务的总体目标描述",
    "steps": [
      {
        "id": "step_1",
        "skill_name": "技能名称",
        "action": "具体动作",
        "entities": { "参数名": "参数值" },
        "depends_on": []
      }
    ]
  }
```

**关键字段说明**:
- `depends_on`: 依赖的步骤 ID 列表,空数组表示不依赖其他步骤
- `goal`: 任务的总体目标,帮助后续分析理解任务意图

---

### 4. 决策规则 (decision_rules)

指导 AI 在不同场景下如何选择响应类型。

#### 何时使用单意图 (when_use_single_intent)

```yaml
when_use_single_intent: |
  - 用户只需要执行一个独立操作
  - 所有必要参数都已明确提供
  - 不需要依赖其他操作的返回值
  - 示例："查询钻石的价格"、"告诉我当前时间"
```

#### 何时使用多步骤任务 (when_use_multi_step)

```yaml
when_use_multi_step: |
  - 任务需要多个独立操作才能完成
  - 后续步骤依赖于前一步骤的结果
  - 某些步骤可能失败，需要条件判断
  - 用户询问多个相关信息，需要调用不同技能
  - 用户的问题包含"同时"、"并且"、"另外"等连接词
  - 用户的问题涵盖多个维度（如：既有商品列表，又有统计信息）
  - 用户使用代词指代（如"这个"、"它"），但具体对象未知，需要先获取
```

#### 何时返回无效意图 (when_return_invalid)

```yaml
when_return_invalid: |
  - 用户输入与任何可用技能都不相关
  - 用户只是闲聊或问候（如"你好"、"谢谢"）
  - 用户输入过于模糊，无法确定具体意图
  - 注意：如果上一轮对话有明确上下文，应该结合历史理解意图，而不是直接返回无效
```

**优化建议**:
- 根据实际使用情况添加更多触发条件
- 提供清晰的正误对比示例
- 定期根据测试数据调整规则

---

### 5. 关键约束规则 (critical_rules)

避免常见错误的硬性规定,优先级最高。

#### 多步骤任务规划规则 (multi_step_mandatory)

```yaml
multi_step_mandatory: |
  【多步骤任务规划规则 - 核心决策流程】
    
  当用户同时询问多个独立问题时，按以下决策流程处理：
    
  **步骤1：识别并列结构**
  - 识别用户问题中的并列结构（如"A和B"、"A与B"、"A、B、C"）
  - 检查每个部分是否可以独立回答
    
  **步骤2：逐个匹配技能（语义匹配原则）**
  - 对每个子问题，检查【可用技能列表】中是否有对应的技能
  - **语义匹配**：技能的用途必须与用户意图完全对应
  - 判断方法：问自己"这个技能的设计目的是什么？用户的问题是否正好是这个技能要解决的？"
  - 反例：用户问"合成配方"，market_query 的设计目的是"查询市场价格"，不是"查询配方"，所以不匹配
  - 只能使用列表中明确存在的技能名称，严禁编造
    
  **步骤3：根据匹配结果选择输出格式**
    
  - **所有子问题都有对应技能** → 返回多步骤格式
  - **部分子问题有对应技能**：
    - 有技能的子问题恰好只有1个 → 返回单意图格式（只执行那一个）
    - 有技能的子问题有2个或以上 → 返回多步骤格式（只包含有技能的步骤）
  - **所有子问题都没有对应技能** → 返回无效意图
  
  **严禁用不相关的技能替代**：
  - **这是导致任务失败的常见原因！**
  - 每个技能都有明确的用途和语义范围
  - **语义匹配**要求技能的用途与用户意图完全对应，不能仅凭功能相似性替代
  - 判断标准：如果技能名称或描述中不包含用户问题的核心关键词，就不是语义匹配
  - 反例：用户问"合成配方"，即使用 market_query 能"查询"，也不匹配，因为 market_query 的语义是"市场商品价格"，不是"配方"
  - 如果某个子问题在【可用技能列表】中找不到语义完全匹配的技能，该子问题就是没有对应技能，不要强行匹配
    
  **关于降级的说明**：
  - 你的职责是识别意图并匹配已有技能，不是完整回答用户的每一个问题
  - 当部分子问题没有对应技能时,返回单意图或多步骤格式执行有技能的部分即可
  - 系统会基于你的识别结果执行对应技能,然后通过LLM二次分析结合执行结果,尽可能完整地回答用户的问题
  - 因此,即使只执行了部分步骤,用户的完整问题仍然可以得到回答
  - 不要因为没有技能覆盖所有问题就返回无效意图,只要有一个子问题有对应技能,就应该返回对应的意图格式
    
  **核心原则**：
  - 只要有一个子问题有对应技能,就必须返回对应的意图格式（单意图或多步骤）
  - 宁可执行部分步骤,也不要完全放弃
  - 严禁在 steps 数组中出现 skill_name: null
  - 严禁编造不存在的技能名称
```

#### 连续对话处理 (continuous_conversation)

```yaml
continuous_conversation: |
  【连续对话处理原则】
  1. 始终结合对话历史理解当前输入
  2. 如果用户使用代词（"这个"、"它"、"那个"）或模糊指令（"再查一下"、"现在呢"），从历史中寻找指代对象
  3. 如果用户说"再查一次"、"同样的问题"，重复上一轮的意图
  4. 如果用户是在询问"当前手持物品"的相关属性且不知道具体物品名,使用多步骤任务:先获取物品信息再执行查询
```

#### 实体参数格式 (entity_format)

```yaml
entity_format: |
  【实体参数格式规范】
  1. 物品格式:使用 "物品名:数量" 格式,如 "钻石:64"、"铁锭:1"
  2. 如果数量为 1,可以省略数量,如 "钻石" 等同于 "钻石:1"
  3. 多个物品用逗号分隔,如 "钻石:10, 金锭:5"
  4. 如果参数不适用,使用 null 或省略该字段
```

**重要性**: 这些规则直接影响意图识别的准确性,修改时需格外谨慎。

**注意**: 实际配置中包含 4 个关键约束规则:
- `placeholder_usage`: 占位符使用限制
- `continuous_conversation`: 连续对话处理原则
- `entity_format`: 实体参数格式规范
- `multi_step_mandatory`: 多步骤任务规划规则（核心决策流程）

### 6. 特殊场景处理指南 (special_scenarios)

处理复杂情况的指导原则。

#### 冲突意图处理 (conflicting_intents)

```yaml
conflicting_intents: |
  【冲突意图处理】
  1. 如果用户输入可能对应多个技能,选择置信度最高的
  2. 如果多个技能都合理,优先选择更具体、更匹配的技能
  3. 在 reasoning 字段中说明选择理由
```

#### 参数缺失处理 (missing_parameters)

```yaml
missing_parameters: |
  【参数缺失处理】
  1. 如果必需参数缺失但有默认值,正常返回意图
  2. 如果必需参数缺失且无法推断,考虑使用多步骤任务先获取参数
  3. 不要编造不存在的参数值
  4. 如果参数完全无法确定,返回无效意图并在 reasoning 中说明
```

#### 技能名称严格限制 (skill_name_restriction)

```yaml
skill_name_restriction: |
  【技能名称严格限制 - 最高优先级规则】
  
  **这是最重要的规则，违反将导致任务失败！**
  
  1. **绝对禁止编造技能名称**
     - 只能使用系统动态提供的【可用技能列表】中明确列出的技能名称
     - 严禁使用任何不在列表中的名称，即使你认为它"应该存在"
     - 严禁根据功能推测技能名称（如：看到"查询配方"就编造 "knowledge_base"、"recipe_query" 等）
  
  2. **严格的白名单机制**
     - 把【可用技能列表】视为唯一的白名单
     - 如果用户需要的功能不在白名单中，视为该功能不可用
     - **严禁用功能不匹配的技能替代**（如用市场查询技能去查合成配方）
  
  3. **严禁在 steps 数组中使用 skill_name: null**
     - steps 中的每个步骤都必须有有效的 skill_name
     - 如果某个子问题没有对应技能，参考【多步骤任务规划规则】中的降级策略
  
  4. **常见错误示例（严禁犯此类错误）**
     - 错误：用户问的功能不在技能列表中，编造一个"看起来合理"的技能名
     - 错误：用户问的功能不在技能列表中，用一个功能相似的技能替代
     - 错误：多步骤任务中出现 {"skill_name": null} 的步骤
     - 正确：检查【可用技能列表】，如果没有语义完全匹配的技能，该子问题视为无对应技能
  
  5. **LLM 的职责边界**
     - 你的职责：识别意图 → 匹配已有技能
     - 不是你的职责：创造新技能、推测技能名称、假设功能存在
     - 如果用户需求超出当前技能范围，诚实说明局限性
```

---

### 7. 输出质量要求 (output_quality_requirements)

确保输出格式的规范性。

```yaml
output_quality_requirements: |
  【输出质量要求】
  1. JSON 格式必须严格正确，可以被解析器解析
  2. 所有字符串值使用双引号，不使用单引号
  3. 布尔值使用 true/false，不使用字符串
  4. 数值类型直接使用数字，不加引号
  5. confidence 值范围：0.0 - 1.0
  6. reasoning 应该简洁明了，说明识别依据
  7. 如果不确定，宁可返回无效意图，也不要猜测错误的技能
  8. 多步骤任务中，确保 depends_on 引用的 step id 确实存在
  9. 避免循环依赖（step_a 依赖 step_b，step_b 又依赖 step_a）
  10. 步骤顺序应该符合逻辑执行顺序
```

## 🔄 提示词构建流程

### 意图识别流程

系统采用 LLM 意图识别机制：

```
用户输入
  ↓
SkillIntentRecognizer（LLM 意图识别）
  ├─ 1. 构建系统提示词（包含所有可用 Skill 描述）
  ├─ 2. 调用 LLM 进行意图分析
  ├─ 3. 解析 JSON 响应
  └─ 4. 判断任务类型
       ├─ 单意图 → SkillIntent
       ├─ 多步骤 → TaskPlan
       └─ 无效意图 → 回退到普通 AI 对话
```

**LLM 意图识别**（全量注入所有 Skill）

系统在每次意图识别时按以下固定顺序构建完整的系统提示词（见 `IntentPromptConfigManager.buildSystemPrompt()` 方法）:

```
1. 【角色定义】
   ↓
2. 【可用技能列表】(动态生成，从已注册的 Skill 中提取，通过参数传入)
   ↓
3. 【响应格式规范】
   ├─ 单意图格式
   ├─ 无效意图格式
   └─ 多步骤任务格式
   ├─ 输出格式强制要求 (output_format_rules)
   ↓
4. 【决策规则】
   ├─ 何时使用单意图
   ├─ 何时使用多步骤任务
   └─ 何时返回无效意图
   ↓
5. 【关键约束规则】
   ├─ 占位符使用限制
   ├─ 连续对话处理原则
   ├─ 实体参数格式规范
   └─ 多步骤任务规划规则
   ↓
6. 【特殊场景处理指南】
   ├─ 冲突意图处理
   ├─ 参数缺失处理
   └─ 技能名称严格限制
   ↓
7. 【输出质量要求】
```

这种结构化设计确保:
- ✅ LLM 接收到的信息层次清晰
- ✅ 重要规则放在前面,优先级高
- ✅ 动态部分(技能列表)插入在合适位置
- ✅ 输出格式要求紧跟响应格式,强化约束

## 🛠️ 使用方法

### 编辑配置文件

1. 打开 `plugins/Kilacraft-AI/intent_prompts.yml`
2. 根据需要修改对应部分的提示词内容
3. 保存文件

### 重载配置

执行以下命令使更改生效:

```bash
/kilacraft reload
```

该命令会一次性重载:
- 主配置 (config.yml)
- 语言配置 (language.yml)
- 技能配置 (skills/)
- **意图识别提示词配置 (intent_prompts.yml)** ✨

权限要求: `kilacraft.reload` (默认仅 OP)

## 💡 优化策略

### 1. 渐进式优化

不要一次性大幅修改配置,而是:

1. 先使用默认配置运行一段时间
2. 观察意图识别日志,记录错误案例
3. 针对性地调整相关规则
4. 每次只改一小部分,便于定位问题
5. 测试验证后再进行下一步优化

### 2. 常见问题排查

#### 问题 1: AI 总是返回单意图,不使用多步骤任务

**症状**: 即使用户的问题明显需要多个步骤,AI 也只返回单个技能调用。

**解决**:
```yaml
decision_rules:
  when_use_multi_step: |
    # 强化触发条件，添加更多具体场景
    - 当用户的问题需要多个独立操作才能完成时
    - 当后续步骤依赖于前一步骤的结果时
    - 当用户询问"我手上的东西有没有卖"这类需要先获取再查询的情况
    - 当用户使用"这个"、"它"等代词但上下文中没有明确指代对象时
```

#### 问题 2: AI 对连续对话处理不当

**症状**: 用户说"现在呢?"、"再查一下",AI 返回 `skill_name: null` 或无法理解上下文。

**解决**:
```yaml
critical_rules:
  continuous_conversation: |
    【连续对话处理原则】
    1. **严禁**直接返回 skill_name: null
    2. 必须分析上一轮对话的核心意图
    3. 如果上一轮是查询状态，则再次执行相同的查询步骤
    4. 示例：用户之前问"我手上是什么"，然后说"那这个能卖吗" 
       → 应该使用多步骤：先获取手持物品，再查询市场
```

#### 问题 3: 占位符使用错误

**症状**: 单意图中出现了 `{step_1.xxx}` 占位符,导致执行失败。

**解决**:
```yaml
critical_rules:
  placeholder_usage: |
    【关键规则】
    1. {step_x.xxx} 占位符 **仅** 在多步骤任务中使用
    2. 单意图的 entities 必须是具体值或 null
    3. 错误示例：{ "entities": { "item": "{step_1.name}" } } ❌
    4. 正确示例：{ "entities": { "item": "钻石:1" } } ✅
```

#### 问题 4: 指代消解不准确

**症状**: 用户说"这个多少钱",AI 无法正确识别"这个"指代的物品。

**解决**:
```yaml
critical_rules:
  continuous_conversation: |
    【连续对话处理原则】
    1. 优先从上一轮对话中寻找明确的物品名称
    2. 如果指代"当前手持物品"且不知道具体名称，必须使用多步骤任务
    3. 不要猜测或编造物品名称
    4. 示例：
       - 上一轮："钻石多少钱？" → AI："100金币" → 用户："那这个呢？"
         → 应识别为查询绿宝石或其他物品的价格（根据上下文）
       - 用户："这个能卖吗？"（无上下文）
         → 应使用多步骤：先 get_player_hand_item，再 query_availability
```

## ⚠️ 注意事项

1. **YAML 格式要严格**:

## 📌 与人格系统的区别

### 意图识别系统 vs 人格系统

| 特性 | 意图识别系统 | 人格系统 |
|------|------------|----------|
| **配置文件** | `intent_prompts.yml` | `personalities.yml` |
| **作用时机** | 所有 AI 交互的入口(关键词触发、连续对话、插件命令) | 仅在插件命令模式下使用(`/kilacraft plugins`) |
| **核心功能** | 识别用户意图,选择 Skill,规划任务步骤 | 定义 AI 的回答风格和语气 |
| **配置内容** | 意图识别规则、响应格式、决策逻辑 | 不同人格的提示词(严厉教师、冒险伙伴等) |
| **是否多实例** | 否,全局唯一一套规则 | 是,可以配置多个人格 |
| **重载命令** | `/kilacraft reload` | `/kilacraft personalities reload` |

### 工作流程示例

#### 场景 1: 玩家通过关键词触发
```
玩家: @ai 我手上是什么?
  ↓
【意图识别】(intent_prompts.yml)
  → 识别为: GenericBukkitAPI.get_player_hand_item
  ↓
【执行 Skill】
  → 获取玩家手持物品
  ↓
【生成回复】(使用默认 system_prompt 或当前人格)
  → "你手上拿着钻石剑"
```

#### 场景 2: 插件命令模式(带人格)
```
控制台: /kilacraft plugins 严厉教师 你好 UUID xxx
  ↓
【意图识别】(intent_prompts.yml)
  → 识别用户输入"你好"的意图(可能是闲聊,返回无效意图)
  ↓
【回退到普通对话】
  → 使用"严厉教师"人格的提示词(personalities.yml)
  ↓
【生成回复】
  → "这位同学,上课时间不要闲聊!有问题就问具体的。"
```

### 关键区别

1. **意图识别是通用的**: 无论使用哪个人格,意图识别的规则都是一样的
2. **人格影响的是回复风格**: 人格只影响最终如何回答,不影响识别用户想做什么
3. **两者独立配置**: 修改人格不会影响意图识别,反之亦然

### 配置建议

- **intent_prompts.yml**: 专注于如何让 AI 更准确地理解用户想要执行什么操作
- **personalities.yml**: 专注于如何让 AI 用不同的风格和语气回答问题

**不要**在 `intent_prompts.yml` 中混入人格相关的描述,这会混淆意图识别的逻辑。

    3. ...

## ❓ 常见问题

### Q: 修改配置后没有生效?

A: 确保执行了 `/kilacraft reload` 命令,并检查控制台是否有错误信息。

### Q: 如何判断配置是否合理?

A: 观察意图识别准确率,如果低于 80%,说明需要优化。重点关注多步骤任务的识别情况。

### Q: 可以针对不同人格使用不同的提示词吗?

A: 当前版本不支持,所有人格共用同一套意图识别提示词。未来版本可能会支持个性化配置。

### Q: 提示词太长会影响性能吗?

A: 会增加 token 消耗和响应时间,但影响较小。建议保持在 2000-3000 tokens 以内。

### Q: 如何回滚到之前的配置?

A: 如果有备份文件,直接替换即可:
```bash
cp plugins/Kilacraft-AI/intent_prompts.yml.backup plugins/Kilacraft-AI/intent_prompts.yml
/kilacraft reload
```
