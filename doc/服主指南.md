## 🎯 为什么选择 Kilacraft-AI？

### ❌ 传统 AI 方案的痛点

- **配置复杂**：需要部署向量数据库、Redis、中间件服务
- **资源占用高**：动辄数 GB 内存，小服根本跑不动
- **维护成本高**：需要专门的技术人员运维
- **功能臃肿**：90% 的功能用不上，却要为它们付费

### ✅ Kilacraft-AI 的优势

| 特性 | 说明 |
|------|------|
| **零中间件依赖** | 只需一个 JAR 文件，无需数据库、缓存等额外服务 |
| **极低内存占用** | 小型服务器仅需 8-12 MB，大型服务器约 30-50 MB |
| **开箱即用** | 5 分钟完成配置，立即投入使用 |
| **性能优化** | HTTP 连接池复用、异步非阻塞执行、流式响应支持 |
| **高度可定制** | 人格系统、知识库、语言配置全部可自定义 |
| **生态友好** | 开放 SPI 接口，第三方插件可无缝接入 |

### 3️⃣ LLM 智能意图识别 + 多步骤任务编排

#### 🧠 什么是智能意图识别？

Kilacraft-AI 不是简单地"回答问题"，而是**理解你的真实意图**并自动调用对应功能！

这是整个 Skill 系统的**大脑**，无论调用的是经济系统、Bukkit API 还是第三方插件的 Skill，都会经过这个智能引擎处理。

```yaml
# Agent 工作流程
用户输入 → LLM 意图识别 → 判断任务类型 → 执行技能/任务 → 分析结果 → 生成回复
```

**核心优势：**
- 🎯 **自然语言理解**：玩家无需记忆命令，直接说人话即可
- 🤖 **自动路由**：AI 自动判断应该调用哪个 Skill
- 🔗 **多步骤编排**：复杂任务自动分解为多个有序步骤
- 💡 **智能总结**：LLM 综合分析所有结果，生成友好回复

```
[Kilacraft-AI] 
    已为你查询：
    • 钻石价格：$80.00/个
```

```
玩家: 我想建个自动化农场，先看看我背包里有没有锄头和水桶，再告诉我现在是不是白天
```

#### 🎯 LLM 结果分析与总结

所有步骤执行完成后，LLM 会进行**二次分析**，综合所有结果生成友好回复：

```
# config.yml 配置
agent:
  prompts:
    # 系统提示词：定义 LLM 在分析阶段的角色
    system_prompt: "你是一个专业的 Minecraft 游戏助手..."
    
    # 分析提示词：指导 LLM 如何分析执行结果
    analysis_prompt: |
      {results}  # ← 所有步骤的执行结果
      请根据以上对话历史、当前输入、执行结果，
      给出综合性的分析和建议，请用简洁友好的语言回复玩家。
```

**为什么需要二次分析？**

原始的技能执行结果通常是**结构化数据**，不适合直接展示给玩家：

```
原始结果:
• step_1: {"item_name": "钻石", "price": 80.0, "stock": 15}
• step_2: {"balance": 12580.0}

LLM 分析后的回复:
"已为你查询：
 • 钻石价格：$80.00/个（库存 15 个）
 • 你的余额：$12,580
 
 💡 分析：购买 10 个钻石需要 $800，你的余额充足，完全可以购买！
 需要我帮你下单吗？"
```

**LLM 分析的优势：**
- 💬 **自然语言转换**：将结构化数据转换为友好的对话
- 🎭 **人格化表达**：根据配置的人格风格调整语气
- 📝 **上下文关联**：结合对话历史，使回复更连贯
- 💡 **智能建议**：基于数据提供有价值的建议

#### ⚙️ 配置灵活可控

```
agent:
  enabled: true                    # 总开关（优先级最高）
  enable_chat_listener: true       # 关键词触发是否启用 Agent
  enable_command: true             # /kilacraft 命令是否启用 Agent
  
  # 历史对话上下文配置
  intent_history_count: 5          # 意图识别时使用 5 轮历史
  analysis_history_count: 2        # 结果分析时使用 2 轮历史
  
  prompts:
    system_prompt: "你是一个专业的 Minecraft 游戏助手..."
    analysis_prompt: "{results}\n请根据以上对话历史、当前输入、执行结果，给出综合性的分析和建议。"
```

**配置说明：**
- `intent_history_count`: 帮助 LLM 理解"再查一下那个物品"等指代性表达
- `analysis_history_count`: 让 LLM 在分析结果时参考对话上下文，使回复更自然
- 可通过关闭 `enable_chat_listener` 或 `enable_command` 在特定入口禁用 Agent 能力

### 4️⃣ 插件命令模式 + 人格系统（高级功能）

插件命令模式是 Kilacraft-AI 为**第三方插件集成**设计的专用接口，允许其他插件通过控制台以指定的人格调用 AI。

**核心设计理念：**
> 插件命令模式不是给服主手动执行的命令，而是**供第三方插件在代码或配置中调用**的 API 接口。

#### 📋 命令格式

```
/kilacraft plugins <人格名称> <消息内容> <玩家 UUID> [回调命令...]
```

**参数说明：**
- `<人格名称>`：在 `personalities.yml` 中定义的人格
- `<消息内容>`：要发送给 AI 的消息
- `<玩家 UUID>`：目标玩家的 UUID
- `[回调命令...]`：**可选**，AI 完成后自动执行的命令（支持 `{response}` 占位符）

**重要特性：**
- 🔒 **仅限控制台执行**
- 🌐 **独立历史记录**：每个 `UUID_人格` 组合独立
- ⏱️ **专用冷却时间**：使用 `plugins_cooldown_seconds` 配置
- 💬 **回调命令支持**：AI 完成后自动执行，`{response}` 替换为实际回复

完整示例见第 7 章。

**核心设计理念：**
> 插件命令模式不是给服主手动执行的命令，而是**供第三方插件在代码或配置中调用**的 API 接口。

#### 📋 命令格式

```
/kilacraft plugins <人格名称> <消息内容> <玩家 UUID> [回调命令...]
```

**参数说明：**

- 🌍 **世界限制检查**：如果目标玩家在线，会检查是否在禁止的世界
- 💬 **回调命令支持**：AI 完成后自动执行指定命令，`{response}` 会被替换为实际回复

#### 💡 核心应用场景：第三方插件集成

插件命令模式适用于**任何需要 AI 能力的第三方插件**，包括但不限于：
- 🤖 **NPC 对话系统**（如 MythicMobs）：让 NPC 拥有智能对话能力
- 🎮 **任务系统**：根据玩家行为动态生成任务描述和奖励
- 📊 **数据分析**：分析玩家行为并生成个性化建议
- 🔧 **管理工具**：自动生成服务器报告、日志摘要等

##### 工作原理

```
第三方插件触发事件
    ↓
执行控制台命令：/kilacraft plugins <人格> <问题> <玩家UUID> [回调命令]
    ↓
Kilacraft-AI 以指定人格生成回复（异步，2-5秒）
    ↓
AI 完成后自动执行回调命令（以控制台身份）
    ↓
你的插件接收回调命令，处理 AI 回复
    ↓
缓存立即删除（一次性消费）
```

##### 完整配置示例

假设你要开发一个插件，让玩家可以通过 NPC 询问服务器规则。

**第一步：定义人格（`personalities.yml`）**

```yaml
# 狐狸人格
狐狸: |
  你是一只聪明的狐狸 NPC，正在和玩家 {player} 对话。
  你说话俏皮可爱，喜欢用"~"结尾，经常使用表情符号。
  你对服务器规则了如指掌，会用有趣的方式解答玩家疑问。
```

**第二步：在你的插件中调用 Kilacraft-AI**

有两种方式发起请求：

**方式 A：在代码中直接调用（推荐用于 Java 插件）**

```java
// 当玩家与 NPC 交互时
@EventHandler
public void onNPCInteract(PlayerInteractEntityEvent event) {
    Player player = event.getPlayer();
    Entity npc = event.getRightClicked();
    
    // 检查是否是特定的 NPC
    if (npc.getCustomName() != null && npc.getCustomName().equals("狐狸 NPC")) {
        // 构建回调命令
        String callbackCommand = String.format(
            "myplugin handle_ai %s %s", 
            "{response}",  // 占位符，会被替换为实际回复
            player.getName()
        );
        
        // 调用 Kilacraft-AI 插件命令
        Bukkit.dispatchCommand(Bukkit.getConsoleSender(), String.format(
            "kilacraft plugins 狐狸 服务器的规则是什么 %s %s",
            player.getUniqueId().toString(),
            callbackCommand
        ));
        
        player.sendMessage("§e狐狸正在思考...");
    }
}
```

**方式 B：在配置文件中调用（推荐用于配置驱动型插件，如 MythicMobs）**

```yaml
# MythicMobs 技能配置示例
fox_npc_skill:
  Skills:
  - cmd{c="kilacraft plugins 狐狸 服务器的规则是什么 <caster.uuid> myplugin handle_ai {response} <caster.name>"} @self
```

> 💡 **提示**：方式 B 适合支持在配置中执行命令的插件（如 MythicMobs、Skript 等），无需编写 Java 代码。

**第三步：实现回调命令处理器**

```java
// 在你的插件主类中注册命令
@Override
public boolean onCommand(CommandSender sender, Command command, String label, String[] args) {
    if (!command.getName().equalsIgnoreCase("myplugin")) {
        return false;
    }
    
    if (args.length == 0) {
        return false;
    }
    
    String subCommand = args[0];
    
    // 处理 AI 回复回调
    if (subCommand.equals("handle_ai")) {
        // args 格式: ["handle_ai", "回复内容...", "玩家名称"]
        // 注意：回复内容可能包含空格，需要正确解析
        
        // 最后一个参数是玩家名称
        String playerName = args[args.length - 1];
        
        // 中间的所有参数是 AI 回复（合并）
        StringBuilder responseBuilder = new StringBuilder();
        for (int i = 1; i < args.length - 1; i++) {
            if (i > 1) responseBuilder.append(" ");
            responseBuilder.append(args[i]);
        }
        String aiResponse = responseBuilder.toString();
        
        // 获取玩家并显示消息
        Player player = Bukkit.getPlayer(playerName);
        if (player != null && player.isOnline()) {
            player.sendMessage("§e[NPC 狐狸] §f" + aiResponse);
        }
        
        return true;
    }
    
    return false;
}
```

**第四步：在 plugin.yml 中注册命令**

```yaml
commands:
  myplugin:
    description: MyPlugin 主命令
    usage: /<command>
```

## ⚠️ 安全与权限管理

### 内置 Skill 安全性

Kilacraft-AI 内置的所有 Skill 都遵循**安全第一**原则：

| Skill 名称 | 功能 | 安全性 |
|-----------|------|--------|
| **MarketQuerySkill** | 查询市场信息（余额、价格、商品列表等） | ✅ 只读，不会消耗物品或金钱 |
| **GenericBukkitAPISkill** | 查询玩家状态、世界信息、服务器信息 | ✅ 只读，仅调用 getter 方法 |

**为什么安全？**
- 📖 **只读操作**：所有内置 Skill 仅查询信息，不修改任何游戏数据
- 🔒 **权限控制**：每个 API 都有独立的权限节点，可通过权限插件精细控制
- 🛡️ **错误隔离**：即使某个 Skill 执行出错，也不会影响其他功能
- 📝 **透明可见**：所有 Skill 定义都在 `skills/` 目录下的 YAML 文件中，可随时审查

### 第三方 Skill 风险提示

如果你安装了第三方插件开发的 Skill，请注意：

**安全风险来源：**
- 第三方开发者可能实现**写操作**（如转账、传送、给予物品等）
- 可能存在**逻辑漏洞**导致意外后果
- 可能**绕过权限检查**执行敏感操作

**防护措施：**
1. **审查 Skill 来源**：只安装可信开发者提供的插件
2. **查看 Skill 描述**：仔细阅读 Skill 的功能说明和返回值
3. **测试环境验证**：先在测试服验证功能是否正常、安全
4. **权限最小化**：通过权限插件限制谁能使用哪些 Skill
5. **监控日志**：定期检查控制台日志，发现异常及时处理

**给开发者的建议：**
如果你是插件开发者，开发 Skill 时请遵循以下原则：
- ✅ 优先实现**只读查询**功能
- ⚠️ 如需实现**写操作**，必须在文档中明确标注风险
- 🔒 在 `execute()` 方法中进行**严格的权限检查**
- 📝 提供清晰的**使用说明**和**注意事项**
- 🛡️ 做好**异常处理**，避免崩溃或数据损坏

详见 [SPI 接入文档](Skill-SPI-接入文档) 第 7 章“错误隔离与异常处理”。

## 📊 性能与资源占用

### 内存占用对比

| 方案 | 内存占用 | 中间件依赖 | 适用服务器规模 |
|------|----------|------------|----------------|
| **Kilacraft-AI** | **8-50 MB**（动态） | **无** | **所有规模** |
| LangChain + Vector DB | 2-5 GB | Redis, PostgreSQL, Elasticsearch | 大型商业服 |
| 自建 RAG 系统 | 1-3 GB | MySQL, Redis | 中大型服 |

> 💡 **说明**：Kilacraft-AI 的内存占用根据知识库规模和在线玩家数量动态变化。小型服务器通常仅需 8-12 MB，大型服务器约 30-50 MB。详见下方详细评估。

### 对话历史内存评估

```
max_history: 10（默认）
每轮对话 ≈ 200 字符 ≈ 0.2 KB
每条消息包含 role + content 字段，实际约 0.3-0.4 KB
100 个活跃玩家 × 20 条 × 0.4 KB = 800 KB
1000 个活跃玩家 × 20 条 × 0.4 KB = 8 MB
```

**结论**：即使千人在线，对话历史占用也不到 10 MB！

**优化建议：**
- ✅ 调整 `max_history` 可控制每个玩家的内存占用
- ✅ 玩家退出后历史记录保留在内存中（重启清空）
- ✅ 使用 `/kilacraft clear` 可手动清除历史记录

**内存占用说明：**
- 📦 **插件本体**：仅占用约 3 MB（JAR 文件大小）
- 💾 **总内存占用 ~50 MB**：包含运行时缓存
  - **知识库缓存**（取决于知识库规模）
    * 原始内容缓存：每个文件完整文本，小型服务器通常 2-5 个文件，约 2-5 KB/文件
    * 分段缓存：按 Markdown 标题或段落分割后的片段，每段最大 500 字符
    * 典型规模：10-20 个文件 × 平均 10 个片段 × 500 字符 ≈ 100-200 KB
    * 大型知识库（50+ 文件）：约 500 KB - 1 MB
  - **对话上下文缓存**（取决于活跃玩家数量）
    * 每个玩家最多保存 10 轮对话（20 条消息）
    * 每条消息平均 200 字符 ≈ 0.2 KB
    * 100 个活跃玩家 × 20 条 × 0.2 KB = 400 KB
    * 1000 个活跃玩家 × 20 条 × 0.2 KB = 4 MB
  - **HTTP 连接池**（固定开销）
    * OkHttpClient 连接池配置：10 个空闲连接，5 分钟超时
    * 每个连接约 50-100 KB（包括缓冲区、Socket 等）
    * 10 个连接 × 100 KB = 约 1 MB
  - **其他运行时对象**
    * 配置对象（ConfigManager、LanguageManager 等）：约 100-200 KB
    * Skill 元数据缓存（Bukkit API 定义、MarketQuerySkill 等）：约 50-100 KB
    * JVM 对象头、类加载等基础开销：约 2-3 MB
  - **实际测试数据**：
    * 小型服务器（10 知识库文件 + 50 在线玩家）：约 8-12 MB
    * 中型服务器（30 知识库文件 + 200 在线玩家）：约 15-25 MB
    * 大型服务器（100+ 知识库文件 + 500+ 在线玩家）：约 30-50 MB

### 性能优化措施

- ✅ **HTTP 连接池**：复用连接，减少握手开销
- ✅ **异步非阻塞**：API 请求不阻塞主线程
- ✅ **配置缓存**：减少重复读取配置的开销
- ✅ **智能重试**：网络波动自动重试，提高稳定性
- ⚠️ **流式输出**：当前版本暂不支持，未来可能作为 Premium 功能提供

### ⚠️ 回调执行与超时保护

**回调命令在主线程执行**：Kilacraft-AI 使用 `Bukkit.dispatchCommand()` 执行回调，该 API 必须在主线程调用（Leaf/Paper 等现代服务端的 AsyncCatcher 机制要求）。

**超时保护机制**：
```yaml
plugin_command:
  callback_timeout_seconds: 3  # 监控主线程命令执行时间
```

**作用范围**：
- ✅ 监控 `Bukkit.dispatchCommand()` 的执行时间
- ✅ 超过设定时间后强制中断主线程的命令执行
- ❌ **不会**中断第三方插件内部的异步任务

**为什么？**

当第三方插件使用异步处理时，`onCommand()` 会立即返回，但异步任务仍在后台运行。Kilacraft-AI 的超时保护只监控主线程的命令执行时间，无法控制第三方插件的异步任务。

**对服主的建议**：

1. **合理设置超时时间**
   ```yaml
   plugin_command:
     # 应该 ≥ 第三方插件的预期处理时间
     callback_timeout_seconds: 5
   ```

2. **理解超时日志**
   ```
   [WARN] 回调命令执行超时 (3s)，已强制中断。命令: myplugin handle_ai ...
   ```
   - 这表示主线程的命令执行被中断
   - 但如果第三方插件使用异步处理，其异步任务仍在运行
   - 这是**正常行为**，不是错误

**对第三方插件开发者的要求**：

如果您的插件使用异步处理，必须：
1. 自行管理超时
2. 检查玩家在线状态
3. 合理设置预期时间并告知服主

### 1. Agent 能力配置

```
agent:
  enabled: true                    # 总开关（优先级最高）
  enable_chat_listener: true       # 关键词触发是否启用 Agent
  enable_command: true             # /kilacraft 命令是否启用 Agent

```

**使用场景：**
- **全入口启用**：适合需要复杂任务处理的服务器
- **仅命令模式启用**：只想在 `/kilacraft` 中提供智能功能
- **全部禁用**：只需要基础 AI 对话功能

### 2. 知识库分段配置

```
knowledge:
  enabled: true
  max_relevant_chunks: 3           # 每次检索最多返回 3 个片段
  segment:
    max_size: 500                  # 每个片段最大 500 字符
    min_size: 25                   # 最小 25 字符（小于此值忽略）
    overlap: 30                    # 片段重叠 30 字符（保持连贯性）
```

**最佳实践：**
- ✅ FAQ 问答式（最推荐）：每个问题一个 `##` 标题

## 🏗️ 系统架构详解

本节深入解析 Kilacraft-AI 的核心架构设计，帮助你全面理解三种交互模式的工作原理、调用链路和设计哲学。

### 🔄 三种交互模式总览

| 模式 | 触发方式 | Agent能力 | 知识库检索 | 回调机制 | 典型场景 |
|------|---------|----------|-----------|---------|----------|
| **ChatListener** | `@ai` 关键词 / 连续对话 | ✅ 启用 | ✅ 智能注入 | ❌ 不需要 | 玩家主动交互 |
| **KilacraftCommand** | `/kilacraft <消息>` | ✅ 启用 | ✅ 智能注入 | ❌ 不需要 | 服主/管理员查询 |
| **插件命令** | `/kilacraft plugins ...` | ❌ 禁用 | ✅ 普通检索 | ✅ 必须 | 第三方插件集成 |

---

### 📊 模式 1 & 2：ChatListener / KilacraftCommand（Agent 开启）

这两种模式共享相同的 Agent 处理流程，区别仅在于触发方式。

#### 完整调用链路

```
用户输入: "@ai 我手上是什么?这个能卖多少钱?"
  ↓
【1. 入口层】ChatListener / KilacraftCommand
  ├─ 检查权限和冷却时间
  ├─ 发送"正在思考..."提示
  └─ 获取历史对话记录
  ↓
【2. 意图识别层】SkillIntentRecognizer
  ├─ 构建系统提示词（包含所有可用 Skill 描述）
  ├─ 调用 LLM 进行意图分析
  ├─ 解析 JSON 响应
  └─ 判断任务类型
       ├─ 单意图 → SkillIntent
       ├─ 多步骤 → TaskPlan
       └─ 无效意图 → 回退到普通 AI
  ↓
【3a. 技能执行层】(如果有有效意图)
  ├─ 单意图路径:
  │   ├─ SkillManager.executeSkillByIntent()
  │   ├─ 执行具体 Skill (如 get_player_hand_item)
  │   └─ 返回 SkillResult { message, data }
  │
  └─ 多步骤路径:
      ├─ TaskExecutor.executeTask()
      ├─ 按依赖顺序执行多个 Skill
      ├─ 数据自动流转 ({step_1.xxx} → step_2)
      └─ 返回综合结果
  ↓
【3b. 二次分析层】LLMAnalysisService ✨ 知识库增强
  ├─ 构建分析提示词:
  │   ├─ [历史记录] (最近 N 轮对话)
  │   ├─ [执行结果] (Skill 返回的数据)
  │   └─ [知识库上下文] ← 新增！
  │        └─ 检索相关知识片段
  │           (服务器规则、物品说明等)
  ├─ 调用 LLM 综合分析
  ├─ 生成自然语言回复
  └─ 返回 SkillResult
  ↓
【4. 响应层】
  ├─ 保存对话到历史记录
  ├─ 显示给玩家
  └─ 完成
```

#### 关键特性

1. **智能意图识别**: LLM 理解用户真实意图，自动选择 Skill
2. **多步骤编排**: 复杂任务分解为有序步骤，数据自动流转
3. **知识库增强**: 二次分析时注入相关知识，提升准确性
4. **失败回退**: 意图识别失败或 Skill 执行出错时，自动转为普通 AI 对话

#### 示例流程

```
用户: "我手上是什么?这个能卖多少钱?"
  ↓
【意图识别】→ 多步骤任务
  ├─ step_1: bukkit_api.get_player_hand_item
  └─ step_2: market_query.query_price (依赖 step_1)
  ↓
【执行技能】
  ├─ step_1 → "钻石剑"
  └─ step_2 → 价格 $500
  ↓
【二次分析 + 知识库增强】
  检索到知识库:
  - 服务器规则: 稀有武器价格上限 $1000
  - 钻石剑属于中等价值物品
  
  LLM 综合分析:
  "你手上是一把钻石剑，市场价 $500。
   根据服务器经济政策，这个价格合理，
   建议在市场中出售。"
  ↓
【返回结果】
```

### 📊 模式 3：插件命令模式（Agent 禁用）

插件命令模式是专为**第三方插件集成**设计的接口，设计理念与普通模式完全不同。

#### 为什么插件命令模式不启用 Agent 能力？

1. **回调机制要求纯文本输出**
   ```java
   executeCallback(callbackCommand, fullResponse);
   //                          ^^^^^^^^^^^^
   //                          必须是 String 类型！
   ```
   - Agent 路径可能返回结构化数据（Map、List 等）
   - 无法保证最终结果是可序列化的纯文本
   - 回调命令需要明确的文本内容作为参数

2. **职责定位不同**
   - ChatListener/KilacraftCommand: "帮我做点什么"（任务执行）
   - 插件命令: "给我一段 AI 生成的文本"（内容创作）

3. **性能考虑**
   - 插件命令可能被高频调用（如 MythicMobs 占位符）
   - 避免不必要的意图识别开销（~2-5秒）
   - 直接调用普通 AI 更快（~1-3秒）

4. **语义清晰**
   - `/kilacraft plugins default 你好 UUID` = "用 default 人格回答'你好'"
   - 不是 "帮我执行某个任务"

#### 完整调用链路

```
控制台: "/kilacraft plugins default 你好 UUID callback_cmd"
  ↓
【1. 入口层】KilacraftCommand.handlePluginsCommand()
  ├─ 验证参数（人格、UUID、回调命令）
  ├─ 检查世界限制和冷却时间
  ├─ 获取隔离的历史记录 (UUID_人格)
  └─ 创建 PluginCommandResponseHandler
  ↓
【2. 人格化配置】
  ├─ 从 personalities.yml 加载人格提示词
  ├─ 替换 {player} 占位符
  └─ 构建完整的 system prompt
  ↓
【3. 普通 AI 对话】LLMProvider.processRequestWithCustomSystemPrompt()
  ├─ 【知识库检索】(在 GenericLLMProvider 内部)
  │   ├─ 检索相关知识片段
  │   └─ 注入到用户消息中
  ├─ 构建请求:
  │   ├─ system: 人格提示词
  │   ├─ history: 隔离的历史记录
  │   └─ user: 用户消息 + 知识库上下文
  ├─ 调用 LLM API (流式响应)
  └─ 返回纯文本回复
  ↓
【4. 回调层】
  ├─ 保存对话到隔离的历史记录
  ├─ 缓存最新回复 (供轮询获取)
  ├─ 执行回调命令:
  │   ├─ 替换 {response} 占位符
  │   ├─ 在主线程执行命令
  │   └─ 超时保护 (默认 3 秒)
  └─ 清理缓存
  ↓
【5. 完成】
```

#### 关键特性

1. **纯文本输出**: 保证回调命令能正确接收和处理
2. **人格化**: 使用指定的人格提示词，风格可控
3. **知识库支持**: 仍然可以检索知识库，增强回答质量
4. **隔离历史**: 每个 `UUID_人格` 组合独立的历史记录
5. **回调机制**: AI 完成后自动执行指定命令

#### 典型应用场景

**场景 1: MythicMobs 占位符集成**
```yaml
# MythicMobs 配置
Skills:
  BossSkill:
    Skills:
      - message{msg=%kilacraft_ai_answer(请问如何打败我?)%}
```

期望输出:
```

     注意躲避我的火焰技能！"
```

**场景 2: 其他插件代码集成**
```java
// 某插件代码
String aiAdvice = plugin.callAI(playerUUID, "这个Boss怎么打?");
player.sendMessage(aiAdvice); // 显示文本建议
```

期望输出:
```
AI: "这个 Boss 有 3 个阶段，第一阶段...
     建议使用火焰抗性药水..."
```

**场景 3: 自动化脚本**
```bash
# 定时任务
/kilacraft plugins daily_tips 今天有什么活动? UUID save_to_file
```

期望输出:
```
AI: "今天的活动有：
     1. 14:00 PVP 大赛
     2. 20:00 建筑比赛
     欢迎参加！"
```

### 🔍 核心差异对比表

| 维度 | ChatListener / Command | 插件命令模式 |
|------|----------------------|-------------|
| **触发方式** | 玩家聊天 / 控制台命令 | 控制台命令 (仅供插件调用) |
| **Agent 能力** | ✅ 启用 (意图识别 + Skill 执行) | ❌ 禁用 (直接普通 AI) |
| **意图识别** | ✅ LLM 自动识别 | ❌ 跳过 |
| **Skill 执行** | ✅ 支持单意图/多步骤 | ❌ 不支持 |
| **知识库检索** | ✅ 二次分析时注入 | ✅ 普通对话时注入 |
| **人格系统** | ❌ 不支持 (仅默认系统提示词) | ✅ 必须 (可指定任意人格) |
| **输出形式** | 多样化 (Skill 结果 + AI 总结) | 纯文本 (必须可序列化) |
| **回调机制** | ❌ 不需要 | ✅ 必须 (传给调用方) |
| **历史记录** | 按玩家 UUID 隔离 | 按 `UUID_人格` 组合隔离 |
| **冷却时间** | 通用 cooldown_seconds | 专用 plugins_cooldown_seconds |
| **响应速度** | ~3-8秒 (含意图识别+Skill) | ~1-3秒 (直接 AI) |
| **适用场景** | 玩家交互、任务执行 | 内容生成、插件集成 |

### 💡 设计哲学总结

#### ChatListener / KilacraftCommand 模式

> "让玩家用最自然的方式与服务器交互，AI 理解意图并执行任务"

- 面向终端玩家
- 强调智能化和自动化
- 支持复杂的任务编排
- 输出灵活多样

#### 插件命令模式

> "为第三方插件提供稳定可靠的 AI 文本生成接口"

- 面向开发者
- 强调稳定性和可预测性
- 输出必须是纯文本
- 支持回调机制

#### 为什么这样设计？

1. **职责分离**: 两种模式服务于不同的目标群体
2. **性能优化**: 插件集成不需要意图识别的开销
3. **可靠性**: 纯文本输出保证回调机制的稳定性
4. **灵活性**: 保留两种模式，满足不同需求

---

### 🎯 如何选择使用哪种模式？

#### 使用 ChatListener / KilacraftCommand，如果：

- ✅ 玩家需要与 AI 进行智能交互
- ✅ 需要执行服务器操作（查询、购买、管理等）
- ✅ 希望 AI 理解复杂的多步骤任务
- ✅ 输出可以是多样化的（数据 + 建议）

#### 使用插件命令模式，如果：

- ✅ 你是插件开发者，需要在代码中调用 AI
- ✅ 只需要 AI 生成的文本内容
- ✅ 需要将 AI 回复传递给其他系统
- ✅ 需要人格化的回复风格
- ✅ 需要回调机制实现自动化流程

## ❓ 常见问题 FAQ

### Q1: API 费用高吗？

**A:** 取决于使用频率。以 DeepSeek 为例：
- `deepseek-chat` 模型：输入 ¥0.5/百万 Token，输出 ¥2/百万 Token
- 单次对话约消耗 500-1000 Token（约 ¥0.001-0.002）
- 建议设置合理的 `cooldown_seconds` 防止滥用

**省钱技巧：**
- 开启冷却时间（默认 5 秒）
- 限制允许的世界（避免在刷怪塔等高频率场景使用）
- 调整 `max_tokens` 控制回复长度

### Q2: 支持哪些 LLM 厂商？

**A:** 支持所有遵循 **OpenAI 标准 API 格式** 的厂商：

| 厂商 | API URL | 推荐模型 |
|------|---------|----------|
| DeepSeek | `https://api.deepseek.com/v1/chat/completions` | `deepseek-chat` |
| 智谱 AI | `https://open.bigmodel.cn/api/paas/v4/chat/completions` | `glm-4-plus` |
| Moonshot | `https://api.moonshot.cn/v1/chat/completions` | `moonshot-v1-8k` |

只需修改 `config.yml` 中的 `api_url` 和 `model` 即可切换，无需改代码！

### Q3: 会不会卡顿服务器？

**A:** 不会。插件采用多项优化措施：
- **极低内存占用**：小型服务器仅需 8-12 MB，大型服务器约 30-50 MB（远低于传统方案的 2-5 GB）
- **异步非阻塞执行**：API 请求在后台线程进行，不阻塞主线程
- **HTTP 连接池复用**：10 个空闲连接复用，减少握手开销
- **可配置冷却时间**：防止高频调用（默认 5 秒）
- **流式响应可选**：降低首字延迟

### Q4: 如何保证数据安全？

**A:** 
- API Key 存储在本地配置文件，不会上传到任何服务器
- 对话历史仅保存在内存中，重启后清空
- 支持世界限制，可在敏感区域禁用 AI 功能
- 权限精细控制，可限制谁能使用哪些功能

### Q5: 支持离线玩家对话吗？

**A:** 
- **普通对话模式**：不支持，AI 对话需要玩家在线才能接收回复。
- **插件命令模式**：支持！控制台可以通过 `/kilacraft plugins` 命令代为调用，即使玩家离线也可以生成 AI 回复（通过回调命令处理）。
- **应用场景**：MythicMobs NPC 可以在玩家离线时预生成回复，等玩家上线后再显示。

### Q6: 如何更新插件？

**A:** 
1. 备份 `plugins/Kilacraft-AI/` 目录（保留配置）
2. 替换 `Kilacraft-AI.jar` 文件
3. 重启服务器
4. 检查新版本的配置项是否有变更

### Q7: 遇到问题怎么办？

**A:** 
1. 开启调试模式：`settings.debug_mode: true`
2. 查看控制台日志，寻找错误信息
3. 检查 API Key 是否正确、网络是否通畅
4. 查阅本文档的"故障排除"章节
5. 在社区论坛或联系作者提问

## 🐛 故障排除

### AI 不回复

**可能原因：**
1. API Key 错误或过期 → 检查 `config.yml` 中的 `api_key`
2. 网络连接问题 → 检查服务器能否访问 API 地址
3. 在被禁用的世界中 → 检查 `banned_worlds` 配置
4. 冷却时间未到 → 等待几秒再试

**解决方法：**
```
# 开启调试模式查看详细日志
settings:
  debug_mode: true
```

### 冷却时间过长

**调整方法：**
```
settings:
  cooldown_seconds: 2  # 改为 2 秒
```

### 连续对话模式无效

**检查项：**
1. `enable_chat_command: true` 是否开启
2. 玩家是否有相应权限
3. 查看控制台是否有错误日志

### 知识库检索不准确

**优化建议：**
1. 使用 Markdown 标题分段（`#`、`##`、`###`）
2. 每个知识点独立成段，避免大段文字
3. 调整 `max_relevant_chunks` 增加返回数量
4. 使用 `/kilacraft knowledge reload` 重新加载

### GlobalMarketPlus 功能不可用

**检查项：**
1. 是否安装了 GlobalMarketPlus 插件
2. 版本是否为 1.3.8.0+
3. 查看控制台是否有集成失败的日志
